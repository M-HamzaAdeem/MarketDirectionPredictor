# Project context

> Read this before any project work. Everything stack-specific lives here so the
> portable kit stays generic.

## Stack — framework & runtime

- **Backend:** Python 3.11+, FastAPI, Uvicorn, SQLAlchemy, SQLite (v1), Pydantic v2 / pydantic-settings, pandas.
- **Frontend:** React 19, Vite, TypeScript (strict), Tailwind CSS v4 (via `@tailwindcss/vite`, no separate config file needed).
- **Monorepo:** `backend/` and `frontend/` are independent projects in the same repo — no shared package manager or build step between them.

## Solution & folder layout

- `backend/app/core/` — `Settings` (env-driven config), enums (`Symbol`, `Timeframe`, `Direction`, `FeedStatus`, `FeedProvider`), logging, exceptions.
- `backend/app/feeds/` — `MarketDataProvider` adapter interface (`connect`/`disconnect`/`stream_ticks`/`fetch_history`/`nominal_status` — every provider implements all five) + implementations: `MockMarketDataProvider` (synthetic; ticks on a virtual clock, not wall-clock time — `time_acceleration`, via `Settings.mock_time_acceleration`, default 60x, compresses a 4H candle into ~4 real minutes; `fetch_history` returns `[]`, a deliberate no-op, since a synthetic feed has no history to backfill), `TwelveDataProvider` (real feed — see below). `factory.py` (`create_provider(settings)`) is the one place that branches on `Settings.feed_provider`; nothing else should. Nothing outside `app/feeds/` should depend on a concrete provider class. There is deliberately **no automatic fallback** from `twelve_data` to `mock` — `create_provider` returns a bare `TwelveDataProvider`, and a real feed failure surfaces loudly as `FeedStatus.DISCONNECTED` via `FeedService`'s existing reconnect-with-backoff (Phase 8) rather than being silently masked with synthetic data; see [[remove-mock-auto-fallback]] in decisions.md for why the earlier `FallbackMarketDataProvider` composite was removed. `mock` remains selectable via `FEED_PROVIDER=mock` for local dev/tests.
- `backend/app/feeds/twelve_data_provider.py` — real market data via [Twelve Data](https://twelvedata.com)'s REST + WebSocket API (`fetch_history` → `GET /time_series`, `stream_ticks` → `wss://ws.twelvedata.com/v1/quotes/price`), selected via `FEED_PROVIDER=twelve_data` + `TWELVE_DATA_API_KEY`. Verified live against a free "Basic" plan account: historical candles and live WebSocket pushes both work for XAU/USD, EUR/USD, and AUD/USD. Two things that aren't obvious from the API and must not regress: (1) `time_series`'s `datetime` field is **not UTC by default** (confirmed empirically — the same candle came back ~10 hours apart depending on the `timezone` param), so every request explicitly passes `timezone=UTC`; (2) forex/commodities are OTC — there is no real trade volume, so every `Tick`/`Candle` this provider produces carries `volume=0.0` (see [[twelve-data-provider]] in decisions.md). `fetch_history` throttles itself to stay under the free tier's 8-requests/minute cap (`_MIN_REQUEST_INTERVAL_SECONDS`); `http_client`/`ws_connect` are constructor-injectable so tests never hit the real network (`httpx.MockTransport` + a hand-rolled fake WS connection, matching this codebase's existing fake-over-mocking-library convention).
- `backend/app/feeds/tradingview_client.py` — **not** a `MarketDataProvider`: TradingView's unofficial WebSocket protocol (no official public API for chart candles) is poll-based (connect → handshake → receive-until-`series_completed` → disconnect per fetch), returning pre-aggregated OHLC bars with the last one always still-forming — a fundamentally different shape from `stream_ticks()`'s continuous tick push, so it gets its own client + orchestrator rather than being forced into the existing abstraction (see [[tradingview-dual-source-pipeline]] in decisions.md). `TradingViewClient.fetch_candles(symbol, timeframe, count)` hand-rolls the `~m~<len>~m~<json>` framing over the existing `websockets` dependency (no new third-party dependency); `ws_connect` is constructor-injectable, same testability pattern as `TwelveDataProvider`. Has its own explicit read timeout (`asyncio.wait_for`) since this is an undocumented protocol with no known keepalive/error framing. Off by default (`Settings.tradingview_enabled`) — this is R&D-grade per TradingView's own terms, not a production data guarantee.
- `backend/app/storage/` — `database.py` (lazy async engine/session factory via `get_engine()`/`get_session_factory()`, both `lru_cache`d — never construct the engine at import time; `init_models()` runs `Base.metadata.create_all` then `migrations.add_missing_columns()` — see below), `migrations.py` (`add_missing_columns` — additive-only schema migration, adds any column an ORM model declares that an existing table is missing, always nullable; explicitly out of scope: renames/type changes/removals, which need a real migration tool — see [[additive-schema-migration]] in decisions.md), `types.py` (`UTCDateTime` — every datetime column must use this, not `DateTime(timezone=True)` directly; see [[utc-datetime-decision]] in decisions.md), `models.py` (`CandleORM`, `PredictionORM` — both append-only, rows never updated; `SignalORM` — the one table this codebase mutates after insert, since a signal has a real lifecycle open→win/loss/expired; `created_at` is the row's wall-clock insert time, distinct from `opened_at`'s candle-derived time; `TradingViewCandleORM`/`TradingViewPredictionORM`/`TradingViewSignalORM` — schema-identical siblings in their own tables for the TradingView pipeline, see below). Every ORM pair shares a plain (unmapped) mixin — `CandleColumns`/`PredictionColumns`/`SignalColumns` — declaring the common `Mapped[...]` columns, so e.g. `CandleORM` and `TradingViewCandleORM` are both genuinely `type[CandleColumns]` (not a false sibling-not-subtype relationship) — this is what makes the repository/service `model=` parameterization below type-correct rather than working only by runtime duck-typing. `repositories/candle_repository.py` translates both ways — reads (`get_recent`/`get_latest`) return domain `Candle` objects, never `CandleORM`; both `save()` (single-candle, live ingestion path) and `save_many_if_missing` (bulk, backfill) now use the same `ON CONFLICT DO NOTHING` idempotent-insert idiom on the `(symbol, timeframe, open_time)` unique index — a live duplicate submission is a routine occurrence for a streaming feed, not automatically a bug, see [[idempotent-live-candle-save]] in decisions.md. All three repositories (`CandleRepository`/`PredictionRepository`/`SignalRepository`) take an optional `model: type[<Columns mixin>]` constructor param defaulting to the Twelve Data ORM class — passing `model=TradingViewCandleORM` etc. operates on the fully separate TradingView table with zero duplicated repository logic; see [[tradingview-dual-source-pipeline]] in decisions.md. `repositories/prediction_repository.py`'s reads still return raw ORM rows (now typed `PredictionColumns`) rather than a domain object — apply the same domain-return refactor there if/when a second caller needs it (YAGNI: don't do it speculatively). `repositories/signal_repository.py` translates `SignalORM`/`TradingViewSignalORM` ↔ the domain `Signal` dataclass both ways, plus `update_outcome()` for resolving a signal.
- `backend/app/api/source_models.py` — the one place `DataSource -> ORM model` is mapped (`candle_model_for`/`prediction_model_for`/`signal_model_for`), so routers and `main.py` share a single definition instead of each hand-rolling an `if source == ...` branch — mirrors `app/feeds/factory.py`'s "one branch point" convention.
- `backend/app/features/` — `indicators.py` (SMA fast/slow, RSI, ATR, momentum, volatility — vectorized pandas functions, periods are named constants), `structure.py` (`SwingPoint`/`detect_swing_points`/`detect_break_of_structure` from Phase 2, plus `detect_sweeps`/`detect_structure_breaks` (CHoCH vs. BOS)/`weak_points` for the ICT pipeline — see [docs/signal-method.md](../../docs/signal-method.md)), `feature_builder.py` (`build_feature_set` — the only entry point the Phase 3 `rule_based.py` strategy should import from this package), `poi.py` (`detect_order_blocks`, `detect_fair_value_gaps` — Point of Interest detection), `fibonacci.py` (`compute_ote_zone` — the 70.5%-79% Optimal Trade Entry zone), `volume_profile.py` (`compute_volume_profile` — Fixed Range Volume Profile, POC/Value Area, used as a POI confluence tiebreaker; returns `None` if every candle in the range has zero volume, not a meaningless "POC" from an all-zero distribution — real forex/commodity feeds report no volume at all, unlike the mock feed's synthetic one).
- `backend/app/prediction/` — `base.py` (`Prediction`/`PredictionSignal` dataclasses + the `PredictionStrategy` ABC — the Phase 3 rule-based path), `rule_based.py` (`RuleBasedStrategy` — v1 weighted-vote heuristic; `RSI_BULLISH_THRESHOLD`/`RSI_BEARISH_THRESHOLD` are public module constants, not underscore-prefixed, specifically because `api/routers/config.py` is a second real reader of them — see [docs/prediction-method.md](../../docs/prediction-method.md); `_combine`'s confidence is scaled against `_TOTAL_POSSIBLE_WEIGHT` (all 4 indicators), not just the weight of votes present, so a lone available indicator voting unanimously reads as partial confidence, not 100% — see [[rule-based-confidence-calibration]] in decisions.md), `ml_strategy.py` (`MLStrategy` — Phase 9 Part C; loads a separate trained scikit-learn classifier per (symbol, timeframe) pair, lazily and cached, keyed off whichever `FeatureSet` it's asked to evaluate — see [[ml-prediction-strategy]] in decisions.md), `factory.py` (`create_strategy(settings)` — the one place that branches on `Settings.prediction_strategy`, mirroring `app/feeds/factory.py`'s pattern), `signal_resolution.py` (`resolve_signal` — pure WIN/LOSS/EXPIRED resolution shared by `SignalTracker` and the backtest engine), `engine.py` (`PredictionEngine` + shared `CANDLE_WINDOW` constant), `signal.py` (`Signal`/`SignalStatus` — the ICT pipeline's domain type; unlike `Prediction`, a `Signal` carries an `id` once persisted because it has a real lifecycle to track; `opened_at` is the tap candle's close_time — a fact about market data — while `created_at` is the row's actual wall-clock insert time, deliberately tracked separately since the two can legitimately differ by hours, see [[stale-entry-tap-and-duplicate-signal]] in decisions.md), `signal_builder.py` (`build_signal` — the 4H bias → 1H setup → 15m entry pipeline; returns `None` unless every stage confirms and R:R ≥ 1.8; `_check_entry`'s tap candle must close *after* `_Setup.earliest_entry_time` (the close_time of the 1H candle that determined `leg_end`) — a candle from the original impulsive move, before the OTE zone was even computable, doesn't count as a genuine retracement into it; see [docs/signal-method.md](../../docs/signal-method.md) for the full writeup). Two independent prediction paths coexist deliberately: `rule_based.py`/`ml_strategy.py` (interchangeable behind `PredictionStrategy`) score every candle close, `signal_builder.py` only ever produces winning-caliber, fully-specified setups.
- `backend/app/ml/` — Phase 9 Part C training pipeline (separate from `app/prediction/ml_strategy.py`, which only *serves* a trained model — this package only ever runs offline via the CLI). `features.py` (`feature_vector(FeatureSet) -> list[float] | None` — the **exact same transform** used at both training and inference time; every value is relative/normalized, never a raw price level, since tree-based models don't extrapolate outside the price range they were trained on and XAUUSD alone has moved from ~2350 to ~4100+ across the backtest's history). `dataset.py` (`build_training_examples` — walks forward through historical candles structurally identical to `run_prediction_backtest`'s loop, labeling each row 1/0 by whether the next candle's close ended up higher). `train.py` (`python -m app.ml.train [--symbol XAUUSD] [--timeframe 1h]` — fetches history directly via a bare `TwelveDataProvider` (same reasoning as `app/backtesting/cli.py`: must fail loudly on a real fetch problem), splits **chronologically** (never shuffled — a random split would leak future rows into training), fits a `RandomForestClassifier` per pair, persists to `Settings.ml_model_dir` (default `data/models/`, gitignored — regenerable binary artifacts, not source), and prints both a holdout accuracy and a walk-forward backtest of the freshly-saved model via `run_prediction_backtest` alongside the rule-based strategy's equivalent number, for a direct, same-run comparison).
- `backend/app/services/` — `candle_aggregator.py` (pure, no I/O — rolls ticks into per-timeframe OHLC `Candle`s), `candle_close_handler.py` (`CandleCloseHandler` — a `Protocol` for anything reacting to a closed candle; `FeedService` holds a `list[CandleCloseHandler]` rather than a named constructor param per reaction, since three now exist), `feed_service.py` (owns the provider lifecycle; per tick: caches latest price + broadcasts a price message; per closed candle: persists it, then runs every registered handler; if the provider's tick stream raises or ends, `_run` reconnects with capped exponential backoff — `_INITIAL_RECONNECT_DELAY_SECONDS`/`_MAX_RECONNECT_DELAY_SECONDS`/`_RECONNECT_BACKOFF_MULTIPLIER` — broadcasting `FeedStatus.DISCONNECTED` for the duration and back to the provider's own `nominal_status` once ticks resume, with no automatic substitution of a different provider (see [[remove-mock-auto-fallback]] in decisions.md); see [[feed-reconnect-backoff]] in decisions.md; `backfill()` fetches+persists missing historical candles per configured symbol/timeframe via `provider.fetch_history()` before `start()` begins live streaming — called explicitly from `main.py`'s `_lifespan`, not automatically inside `start()` — one symbol/timeframe failing doesn't abort the rest; see [[historical-backfill]] in decisions.md), `connection_manager.py` (registry of live WebSocket clients; best-effort broadcast; one instance shared by both pipelines), `broadcast_service.py` (translates domain `Tick`/`Prediction`/`FeedStatus`/`Signal` into `app/schemas/websocket_messages.py` wire types; the only thing that imports `ConnectionManager`; constructed with a fixed `source: DataSource` that gets stamped onto every message it builds — `main.py` builds one instance per pipeline rather than threading `source` through every call site), `prediction_service.py` (`CandleCloseHandler` — event-driven Phase 3 prediction scheduling; see [[event-driven-prediction-scheduling]] in decisions.md), `signal_tracker.py` (`CandleCloseHandler` — resolves OPEN signals to WIN/LOSS/EXPIRED against each new candle of the signal's own `entry_timeframe`; a candle hitting both stop and target is conservatively scored a LOSS), `signal_service.py` (`CandleCloseHandler` — only acts on 15m candle closes; checks `SignalRepository.get_open(symbol)` first and returns early if one is already open (`build_signal()` is a stateless rescan and will keep re-deriving the same still-valid setup on every subsequent 15m close otherwise — see [[stale-entry-tap-and-duplicate-signal]] in decisions.md), otherwise fetches the 4H/1H/15m windows and runs `build_signal()`, persisting+broadcasting anything produced). All three of `prediction_service.py`/`signal_tracker.py`/`signal_service.py` take the same optional `*_model` constructor params as the repositories (defaulting to the Twelve Data ORM classes), so a second, fully parallel set of these three services can run against the TradingView tables with zero duplicated handler logic.
- `backend/app/services/tradingview_feed_service.py` — `TradingViewFeedService`, the poll-based sibling of `FeedService` for the TradingView pipeline (see `tradingview_client.py` above and [[tradingview-dual-source-pipeline]] in decisions.md). Does **not** use `CandleAggregator` — TradingView already hands back pre-aggregated OHLC bars. Each poll cycle: fetches a small fixed window (`_POLL_FETCH_COUNT`, currently 20) per symbol/timeframe, excludes the last (always still-forming) bar, diffs the rest against `CandleRepository.get_recent`'s known `open_time`s *before* persisting (since `save_many_if_missing` doesn't report which rows were new, and this service needs exactly that to know which bars are genuine "candle closed" events), persists via the same idempotent `save_many_if_missing`, then runs `candle_close_handlers` only for the genuinely-new ones. Polls timeframes **coarsest-to-finest per symbol** every cycle (`_ordered_timeframes`) — required because `SignalService` reads the 4H/1H windows the instant a 15m candle closes, so a poll cycle that discovers newly-closed 4H/1H/15m bars simultaneously must persist the coarser ones first, a hazard the tick-driven path never has (`CandleAggregator` only ever emits one tick's worth of closes at a time). Same backoff-on-failure/status-broadcast shape as `FeedService._run`, adapted to "poll cycle raised, back off" instead of "stream ended, reconnect." Known limitation: an outage longer than `_POLL_FETCH_COUNT` bar-intervals silently loses those candles until the next full restart re-runs `backfill()` — see [TD-9](tech-debt.md).
- `backend/app/api/routers/` — REST endpoints, one router per resource: `health.py`, `config.py` (`GET /config` — curated, **read-only** view of effective `Settings` + the ICT/prediction module constants + `tradingview_enabled`; no PUT/PATCH, since `Settings` is `lru_cache`d at startup and the strategy constants aren't persisted config yet — see `docs/architecture.md`'s Phase 7 note), `symbols.py`, `prices.py` (latest tick per symbol from `FeedService`'s in-memory cache, falling back to the latest closed 1m candle when a symbol hasn't ticked yet this session — see [[price-fallback-to-latest-candle]] in decisions.md; 503s if `?source=tradingview` is requested while that pipeline is disabled), `candles.py` (recent closed candles from SQLite), `predictions.py` (Phase 3 rule-based: `GET .../latest` computes on demand and logs; `GET .../history` reads back), `signals.py` (ICT pipeline: `GET /signals/open` optionally filtered by symbol, `GET /signals/{symbol}/history` including resolved outcomes, and `GET /signals/{symbol}/latest` — the one endpoint that can create a signal outside of `SignalService` reacting to a live 15m close, mirroring `predictions.py`'s on-demand pattern but reusing the exact same open-signal/eligible-tap guards `SignalService` applies live, since a `Signal` has a real lifecycle unlike a stateless `Prediction`), `websocket.py` (`/ws` — broadcast-only; sends the connecting client both pipelines' `FeedStatus` immediately on connect (TradingView's only if enabled), then just drains incoming messages to keep the socket alive). Symbol/timeframe are typed enum path params everywhere, not free text. All four data-bearing routers (`candles.py`/`predictions.py`/`signals.py`/`prices.py`) additionally take `source: DataSource = Query(default=DataSource.TRADINGVIEW)` — a query param, not a path segment, since it's a view/filter modifier on an already-fully-identified resource (matching the existing `limit` convention) rather than part of identifying the resource the way `Symbol`/`Timeframe` are; resolved to the right ORM model via `app/api/source_models.py`. TradingView is the default source project-wide (`Settings.tradingview_enabled` defaults `True`) since, unlike Twelve Data, it needs no API key — see [[tradingview-default-source]] in decisions.md.
- `backend/app/api/dependencies.py` — shared FastAPI dependency accessors: `get_feed_service` (reads `request.app.state.feed_service`), `get_tradingview_feed_service` (reads `request.app.state.tradingview_feed_service`, `None` when `Settings.tradingview_enabled` is False — used by `prices.py`), `get_prediction_engine` (`lru_cache`d — same lazy-construction pattern as `storage/database.py`, so it stays import-side-effect-free and overridable in tests; calls `app/prediction/factory.py`'s `create_strategy(get_settings())` rather than hardcoding `RuleBasedStrategy()` — safe as a singleton even for `MLStrategy`, since it's symbol/timeframe-agnostic at construction and resolves which per-pair model to use internally, per-call; shared by both pipelines' `PredictionService` instances, since the strategy itself has no source/table coupling; move to `app.state` if a future strategy needs genuinely per-request state).
- `backend/app/main.py` — `create_app()` factory; the mock feed is started/stopped via a FastAPI `lifespan` context manager, not `on_event` (deprecated). No module-level side effects beyond the final `app = create_app()`, so tests can build isolated instances. `app.middleware("http")(add_security_headers)` is registered before the CORS middleware. `_build_candle_close_handlers(broadcaster, session_factory, *, candle_model=..., prediction_model=..., signal_model=...)` builds one pipeline's `[PredictionService, SignalTracker, SignalService]` handler triad (order matters — see the services bullet above); `_lifespan` calls it once for the always-on Twelve Data pipeline and, if `Settings.tradingview_enabled`, again with the TradingView ORM classes for a second, fully independent `TradingViewFeedService` — extracted specifically because the two call sites would otherwise be ~25-line near-duplicates, crossing this project's own "second real caller" extraction threshold (see [[tradingview-dual-source-pipeline]] in decisions.md). `app.state.tradingview_feed_service` is always set (to `None` when disabled), so downstream code (`websocket.py`, `dependencies.py`) never needs to guess whether the attribute exists.
- `backend/app/core/security_headers.py` — `add_security_headers` (a plain `@app.middleware("http")`-style function, not a class) sets CSP/`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/HSTS on every HTTP response; doesn't touch the `/ws` handshake. The CSP allow-lists `cdn.jsdelivr.net` specifically so FastAPI's built-in `/docs` (Swagger UI) keeps working under a `default-src 'self'` policy.
- `backend/pytest.ini` — sets `pythonpath = .` (so `app.*` imports resolve regardless of invocation cwd), `asyncio_mode = auto` (async `def test_...` functions run without a `@pytest.mark.asyncio` decorator on every one), and `addopts = --cov=app --cov-report=term-missing --cov-fail-under=80` (Phase 8) — a bare `pytest` run always enforces the 80% coverage gate from [.claude/rules/code-review.md](../rules/code-review.md); no separate `.coveragerc`, since the repo-wide total (89% as of Phase 8) already clears the threshold without needing per-file `omit` tuning.
- `frontend/src/types/` — `market.ts` (`MarketSymbol`/`Timeframe`/`Direction`/`FeedStatus`/`Candle`/`Price`/`DataSource` + `ALL_DATA_SOURCES`), `prediction.ts`, `signal.ts`, `websocket.ts` (`WebSocketMessage` discriminated union — every variant carries a required `source: DataSource` field, stamped by the backend's `BroadcastService`). Field names deliberately match the backend's wire format (snake_case) exactly — no camelCase transform layer, to avoid a hand-maintained mapping that could drift from the API.
- `frontend/src/services/` — `apiClient.ts` (`apiGet<T>`, `ApiError`), `api.ts` (one function per REST endpoint: `getSymbols`, `getPrices`, `getCandles`, `getSignalHistory`, `getSignalLatest` — the on-demand `GET /signals/{symbol}/latest`, 404s if there's neither an open signal nor a winning-caliber setup right now — `getPredictionLatest` — the on-demand `GET /predictions/{symbol}/{timeframe}/latest`, 404s if no closed candle exists yet for that pair). Every function except `getSymbols`/`getConfig` takes a `source: DataSource = 'twelve_data'` param, appended as a `?source=` query string param matching the backend routers. `getOpenSignals`/`getPredictionHistory` were both removed along with their only callers (`useOpenSignalsBootstrap.ts`, replaced by `useSignalsBootstrap.ts`; the Prediction History table) — the underlying `GET /signals/open`/`GET /predictions/{symbol}/{timeframe}/history` backend endpoints themselves are untouched, just currently unconsumed by the frontend.
- `frontend/src/store/marketStore.ts` — a Zustand store fed by the WebSocket (`useMarketSocket`). Every slice (`feedStatus`, `prices`, `predictions`, `signals`) is keyed first by `DataSource` (`Record<DataSource, X>`, both sources' data held simultaneously since both pipelines run continuously regardless of what's displayed), plus one UI-only `activeSource` field for which source the dashboard currently shows. Derived selector hooks — `useActiveFeedStatus`/`useActivePrices`/`useActivePredictions`/`useActiveSignals`/`useActiveOpenSignals` — read whichever source is active, so most components use one of these instead of indexing into the source-keyed slice themselves. Only `useActiveOpenSignals` needs `useShallow` (it wraps `selectOpenSignals(state, source)`, which derives a filtered+sorted array); the others are plain property lookups into an already-stored object, referentially stable as-is. `selectOpenSignals` gains a `source` param — **any selector like it that returns a new array/object per call must be wrapped in `useShallow` from `zustand/react/shallow`** at the call site, or React's `useSyncExternalStore` treats every render as a new snapshot and infinite-loops (`"The result of getSnapshot should be cached"` — hit and fixed in `SignalFeed.tsx`). See `marketStore.test.ts` for pure-logic tests (source isolation, `hydrateSignals`' live-update-wins-over-hydration merge precedence).
- `frontend/src/hooks/` — `useMarketSocket.ts` (owns the WebSocket connection + reconnect with capped exponential backoff, reset to the initial delay on a successful `onopen`; dispatches every message by `message.source` into the store; `onerror` surfaces `disconnected` for *both* sources — not just one — since they share this one socket connection; on a `prediction` message, invalidates `useCandles`' React Query cache via the exported `candlesKey(symbol, timeframe, source)` — `prediction` fires on every candle close for every symbol/timeframe, making it a reliable staleness proxy, unlike `price` which fires on every tick; on a `signal` message, invalidates `useSignalHistory`'s cache via `signalHistoryKey(symbol, source)` the same way — `source` is part of both query keys themselves (not just a request param), so a TradingView candle-close can never invalidate the Twelve Data cache entry for the same pair or vice versa — see [[websocket-driven-query-invalidation]] and [[tradingview-dual-source-pipeline]] in decisions.md), `useSymbols.ts`, `useSignalsBootstrap.ts` (React Query fetch-once-on-mount, fans out `getSignalLatest` across `ALL_DATA_SOURCES` x `ALL_SYMBOLS` via `Promise.allSettled` to seed `signals` — the already-open signal if one exists, or one computed on demand if none is, rather than waiting for the next live 15m close; replaces the older `useOpenSignalsBootstrap.ts`, which only ever read existing open signals and never triggered on-demand creation), `usePredictionsBootstrap.ts` (same pattern, fans out `getPredictionLatest` across `ALL_DATA_SOURCES` x `ALL_SYMBOLS` x `ALL_TIMEFRAMES` via `Promise.allSettled` to seed `predictions` immediately rather than waiting for a live candle close per pair — see [[predictions-bootstrap-on-demand]] in decisions.md), `usePricesBootstrap.ts` (same pattern again, one `GET /prices` call per source seeds `prices` — needed because a lower-liquidity pair like AUDUSD can go a long stretch without a single live tick even though its candles/predictions are already populated; skips a source that 503s, i.e. TradingView disabled, the same way the others skip a 404; see [[price-fallback-to-latest-candle]] in decisions.md). All three bootstrap hooks fetch **both** sources regardless of which is currently active, so toggling `SourceToggle` never needs a refetch. `useCandles.ts` (exports `candlesKey(symbol, timeframe, source)`, the query-key builder shared with `useMarketSocket`), `useSignalHistory.ts` (exports `signalHistoryKey(symbol, source)` the same way) — both React Query wrappers for the Symbol Detail view, refetching automatically when the selected symbol/timeframe/source changes since they're all in the query key.

resolved signals show `realized_rr` instead), `SignalFeed.tsx` (the dashboard's centerpiece), `PredictionPanel.tsx` (a pivot table — rows are `ALL_SYMBOLS`, columns are `ALL_TIMEFRAMES` + an "Overall" column computed by `utils/predictionOverall.ts`'s `computeOverall`, chosen over one-row-per-(symbol,timeframe) specifically to reduce vertical height), `SymbolTimeframeSelector.tsx`, `SourceToggle.tsx` (only rendered when `useConfig()`'s `tradingview_enabled` is true; reads/writes `marketStore`'s `activeSource` — both pipelines keep running in the backend regardless of which is selected here), `PriceChart.tsx` (`lightweight-charts` candlestick series, 480px tall; entry/stop/target drawn as price lines for the open signal on that symbol, if any; takes `symbol`/`timeframe` props — `utils/priceFormat.ts`'s `pricePrecision(symbol)` sets 4-decimal price precision for EURUSD/AUDUSD vs the 2-decimal default for XAUUSD, shared with the chart's own `priceFormat` option so the two can't drift; shifts every candle's displayed timestamp by +5h — `DISPLAY_UTC_OFFSET_SECONDS` — baked into the data itself via a custom `tickMarkFormatter`/`localization.timeFormatter` reading back with UTC getters, so the axis reads correctly regardless of the viewer's own browser timezone; see [[chart-utc-plus-5-display-offset]] in decisions.md; the container carries `role="img"` + an `aria-label` computed by `utils/describeChart.ts` summarizing symbol/timeframe/candle count/current price, since the canvas itself has no accessible content — see [[chart-accessibility-aria-label]] in decisions.md; takes an optional `formingCandle` prop — a live, still-forming bar drawn via a *second*, separate effect calling `series.update()` rather than folding it into the `candles`/`setData()` effect, specifically so a live tick updates just the rightmost bar without resetting the chart's zoom/pan the way a full `setData()` would — see [[live-forming-candle-chart-overlay]] in decisions.md), `SignalHistoryTable.tsx`, `PerformanceStats.tsx` (win rate / avg realized R:R / totals, computed client-side from fetched signal history — no backend aggregation endpoint, YAGNI until a second consumer needs one), `SymbolDetail.tsx` (assembles the selector + chart + stats + signal history table; owns the local `symbol`/`timeframe` selection state, reads `activeSource` from the store; passes `useFormingCandle(symbol, timeframe)`'s result into `PriceChart` as `formingCandle`; the Prediction History table was removed by request — its underlying `usePredictionHistory.ts` hook and `getPredictionHistory` API wrapper were deleted too as dead code, not just unwired).
- `frontend/src/hooks/useFormingCandle.ts` — `useFormingCandle(symbol, timeframe): Candle | null`, tracking a live still-forming candle client-side from price ticks (`useActivePrices()[symbol]`). Neither backend pipeline ever persists the currently-forming bar (`TradingViewFeedService._split_forming` / `CandleAggregator` both discard it), so without this the chart's rightmost bar is always the last *closed* one — one bar behind a live chart like TradingView's own — see [[live-forming-candle-chart-overlay]] in decisions.md. Resets to `null` on a `symbol`/`timeframe` change (no carrying stale OHLC state across a selector switch); guards against a stale/duplicate price tick re-folding via a monotonic-timestamp check, since both the live WebSocket tick and `usePricesBootstrap`'s fallback seed write to the same store slot.
- `frontend/src/utils/performanceStats.ts` — `computePerformanceStats` (pure; win rate excludes `expired`/`open` from the denominator, average realized R:R is over WIN/LOSS only). First piece of frontend business logic worth a unit test — see `performanceStats.test.ts` and the Vitest setup below.
- `frontend/src/utils/currentRiskReward.ts` — `computeCurrentRiskReward(direction, entry, stop, currentPrice)` (pure; returns the live position in R-multiples — 0 at entry, -1 at stop, the full `risk_reward` value at target; `null` for a neutral direction or zero-risk entry==stop edge case). Used only by `SignalCard.tsx` for open signals.
- `frontend/src/utils/priceFormat.ts` — `pricePrecision(symbol)` (pure; 4 decimals for EURUSD/AUDUSD, 2 for XAUUSD). Single source of truth shared by `PriceChart.tsx`'s actual chart rendering and `describeChart.ts`'s aria-label text, so the two can't disagree about a symbol's precision.
- `frontend/src/utils/describeChart.ts` — `describeChart(symbol, timeframe, candles)` (pure; builds `PriceChart.tsx`'s `aria-label` text — see [[chart-accessibility-aria-label]] in decisions.md).
- `frontend/src/utils/formingCandle.ts` — `bucketStart(timestamp, timeframe)` (pure; floors an ISO timestamp to its timeframe bucket in UTC, the client-side twin of the backend's `app/utils/time.py bucket_start()` — the two `TIMEFRAME_SECONDS` maps are manually kept in sync, no shared schema between the stacks, see [TD-10](tech-debt.md)), `updateFormingCandle(previous, price, timestamp, timeframe)` (pure; folds one price tick into a running OHLC state), `formingCandleIsStale(formingOpenTime, lastClosedOpenTime)` (pure; compares epoch instants, not raw ISO strings — the two sides' timestamps use different valid ISO 8601 renderings of UTC, so string comparison isn't a safe proxy for chronological order). Backing `useFormingCandle.ts` above.
- `frontend/src/utils/predictionOverall.ts` — `computeOverall` (pure; extracted out of `PredictionPanel.tsx` specifically because oxlint's `react(only-export-components)` rule flags a component file exporting a non-component function — Fast Refresh needs component files to only export components). A direction only wins the "Overall" call if it leads the other by more than one timeframe's vote (`OVERALL_MARGIN_THRESHOLD`); anything closer, including exact ties, reports `"mixed"`. This rule was reverse-engineered from a hand-worked example, not a documented spec — revisit if it turns out not to match actual intent. See `predictionOverall.test.ts`.
- `frontend/src/components/layout/AppShell.tsx` — shared header (title + nav links via `react-router-dom`'s `NavLink`) + `DisclaimerBanner` + `SourceToggle` + `FeedStatusIndicator`, wrapping `children` in a `<main>`. Both `DashboardPage` and `SettingsPage` render through it so the chrome (nav, disclaimer, source toggle, feed status) can't drift between pages.
- `frontend/src/hooks/useConfig.ts` — React Query wrapper around `getConfig()` (`GET /config`); read-only, no mutation hook, matching the backend's read-only `/config` endpoint.
- `frontend/src/pages/DashboardPage.tsx` — assembles the dashboard sections inside `AppShell`; does **not** call `useMarketSocket()` itself.
- `frontend/src/pages/SettingsPage.tsx` — read-only grouped display of `useConfig()`'s data (Feed / Prediction / ICT Signal Pipeline / Rule-Based Prediction Thresholds sections), inside `AppShell`. The "Prediction" section shows `config.prediction_strategy` (`"rule_based"` or `"ml"`) — the rule-based thresholds section always shows those module constants regardless of which strategy is actually active, since they exist unconditionally in the codebase.
- `frontend/src/App.tsx` — calls `useMarketSocket()` exactly once, above `<Routes>` (`/` → `DashboardPage`, `/settings` → `SettingsPage`), so the WebSocket connection survives route navigation instead of reconnecting per page — see [[websocket-hook-at-app-level]] in decisions.md. `main.tsx` wraps the tree in `BrowserRouter` + `QueryClientProvider`.
- `backend/app/backtesting/` — walk-forward backtesting over real historical data, avoiding lookahead bias (a simulated "as of" point may only see candles that would genuinely have closed by then). `signal_resolution.py` (in `app/prediction/`, not this package) holds `resolve_signal()`, extracted from `SignalTracker` so live and backtested outcomes are graded by the identical rule. `signal_backtest.py` (`run_signal_backtest`) replays `build_signal()` at every 15m close using a two-pointer walk (O(n), not re-filtering the whole history per step) to window 4H/1H/15m candles as-of each point, tracking at most one open signal at a time — mirroring the live ordering (`SignalTracker` resolves before `SignalService` creates) — so the same rediscovered setup can't be appended as multiple duplicate signals, see [[backtest-duplicate-signal-fix]] in decisions.md; `prediction_backtest.py` (`run_prediction_backtest`) replays the rule-based `PredictionEngine`/`RuleBasedStrategy` per timeframe, scoring each non-neutral call against whether the very next candle's close moved the predicted direction (this is what finally gives [TD-2](tech-debt.md) real evidence instead of a guess). Both engines' window sizes are constructor-overridable (defaulting to the real live constants from `signal_service.py`/`engine.py`) specifically so tests don't need 60+/100+/20+ real candles to exercise the walk-forward/warmup logic. `models.py` (`BacktestRun`/`BacktestKind`) is the persisted-run domain type. `cli.py` (`python -m app.backtesting.cli`) is the only way to actually run a backtest — it fetches history directly via a bare `TwelveDataProvider`, not through `factory.py`'s `create_provider()`, since a backtest must always use real data regardless of the running app's configured `feed_provider` and must fail loudly on a real fetch problem, not produce a meaningless result, prints a summary, and persists it. See [[backtesting-engine]] in decisions.md.
- `backend/app/storage/models.py` — `BacktestRunORM` (append-only, like `CandleORM`/`PredictionORM` — a backtest run is a point-in-time fact, never mutated after saving); `repositories/backtest_run_repository.py` translates it to/from the domain `BacktestRun`. `summary` is JSON-encoded (matching `SignalORM.details`'s convention) since its shape differs by `kind` (signal vs. prediction backtests report different stats).
- `backend/app/api/routers/backtests.py` — `GET /backtests` (optionally filtered by `symbol`/`kind`), read-only — no POST; a run is only ever produced by the CLI, which needs unthrottled, potentially minutes-long access to a real feed provider that a request/response cycle isn't suited for (YAGNI on background-job infrastructure until there's real demand for on-demand backtests from the UI).
- `docs/architecture.md` — full architecture + phase plan; keep in sync when the design changes.

## Key libraries

- **Backend config:** `pydantic-settings` — single `Settings` class in `app/core/config.py`, cached via `get_settings()`. Env vars map case-insensitively to field names (no prefix); list fields (`cors_origins`, `symbols`, `timeframes`) accept comma-separated strings via a `field_validator`. `tradingview_enabled`/`tradingview_exchange`/`tradingview_poll_interval_seconds` gate and configure the optional second pipeline (`TRADINGVIEW_ENABLED=true` in `.env` to turn it on — see `.env.example`) — defaults off since it depends on an unofficial protocol.
- **Backend numerics:** `pandas`/`numpy` for indicator math (`app/features/indicators.py`) — vectorized over Series, not manual loops. Indicator periods (RSI/ATR 14, SMA 10/30, momentum 10, volatility 20) are named module constants, not tuned yet; revisit once backtesting (Phase 9) can score them.
- **Backend data access:** SQLAlchemy 2.0 async engine + `aiosqlite` driver (`sqlite+aiosqlite:///...`) — kept async to match the rest of the backend's async-throughout convention; see [[async-sqlalchemy-decision]] in decisions.md. Repositories own sessions; no ORM models leak past the repository layer — routers/services only ever see the domain `Candle`/`Tick` dataclasses from `app.feeds.base`.
- **Backend HTTP client:** `httpx.AsyncClient` — used both for the FastAPI test client and as `TwelveDataProvider`'s REST client (constructor-injectable so tests substitute `httpx.MockTransport` instead of hitting the real API; no `respx` or other mocking library added, per this codebase's hand-rolled-fake convention).
- **Backend WebSocket client:** `websockets` (already a dependency for the server side of `/ws`) doubles as `TwelveDataProvider`'s client for Twelve Data's real-time price stream, and again as `TradingViewClient`'s transport for TradingView's unofficial protocol (hand-rolled `~m~<len>~m~<json>` framing on top of it — no new dependency added for the second data source); `ws_connect` is constructor-injectable on both for the same testability reason.
- **Backend ML:** `scikit-learn` (`RandomForestClassifier`) + `joblib` (model (de)serialization) — added Phase 9 Part C, per PROJECT.md's stated stack ("Scikit-learn or XGBoost for first ML model"). scikit-learn chosen over XGBoost for v1: lighter dependency, no native build toolchain concerns, sufficient for a 6-feature tabular classifier; XGBoost is a reasonable fast-follow if accuracy needs it. See [[ml-prediction-strategy]] in decisions.md.
- **Backend testing:** pytest + pytest-asyncio + FastAPI `TestClient`/httpx, plus `pytest-cov` (Phase 8) for the coverage gate — see `pytest.ini` above. Test files must have a unique basename across `tests/unit/` and `tests/integration/` — neither directory has `__init__.py`, so two files sharing a name (e.g. `test_signal_tracker.py` in both) causes a pytest "import file mismatch" collection error. Suffix one (e.g. `_persistence`) if a name collision comes up.
- **Frontend styling:** Tailwind v4 utility classes directly in JSX; no CSS Modules/styled-components.
- **Frontend data fetching:** `@tanstack/react-query` for REST (one-shot fetch-and-cache, e.g. `useSymbols`, `useSignalsBootstrap`) — not a hand-rolled `useEffect` fetch per component. `QueryClientProvider` wraps the tree in `main.tsx`.
- **Frontend live state:** `zustand` (`store/marketStore.ts`) for WebSocket-pushed state — push-driven data doesn't fit react-query's pull/cache model, so REST bootstraps initial state and the store takes over from there via `useMarketSocket`.
- **Frontend charting:** `lightweight-charts` v5 (free/Apache-2.0 tier) — series are created via `chart.addSeries(CandlestickSeries, options)` (the v5 tree-shakeable pattern; `CandlestickSeries` is a value import from the package, not a string). Price lines (`series.createPriceLine`) draw entry/stop/target; there's no "clear all price lines" API, so callers must track and `removePriceLine` the ones they created (see `PriceChart.tsx`'s cleanup effect). **The "TradingView" attribution logo on the chart must not be hidden or removed** — it's a license condition of the free tier, not a stray artifact; only TradingView's paid Advanced Charts library allows removing it.
- **Frontend testing:** Vitest (`npm test`) — added in Phase 6 for the first genuinely testable piece of business logic (`utils/performanceStats.ts`). No React Testing Library yet; add it when a component's behavior (not just a pure function) needs testing.
- **Frontend routing:** `react-router-dom` v7 — added in Phase 7 for the `/` (dashboard) and `/settings` routes. `BrowserRouter` wraps the tree in `main.tsx`; `App.tsx` only holds `<Routes>` plus the single `useMarketSocket()` call (see [[websocket-hook-at-app-level]] in decisions.md).

## Conventions & namespaces

- **Backend:** modules import as `app.<package>.<module>`; async I/O throughout (no sync-over-async); enums (`Symbol`, `Timeframe`, `Direction`, `FeedStatus`) instead of magic strings anywhere a value is one of a fixed set.
- **Frontend:** camelCase functions/variables, PascalCase components/types, kebab-case CSS classes/ids; TypeScript `strict: true` is enabled in `tsconfig.app.json`.
- **Feed provider swap:** adding a new market data source means a new class implementing `MarketDataProvider` in `app/feeds/` plus one branch in `app/feeds/factory.py`'s `create_provider` — never a second branch ladder scattered across calling code (`main.py` only ever calls `create_provider(settings)`).
- **Prediction strategy swap:** same pattern — a new class implementing `PredictionStrategy` in `app/prediction/` plus one branch in `app/prediction/factory.py`'s `create_strategy`; `api/dependencies.py`'s `get_prediction_engine()` only ever calls `create_strategy(get_settings())`.
- **No auto-trading:** there is no execution/order-placement module in this codebase by design, not as a disabled feature. Do not add one without an explicit, separate decision from the project owner.

## Build & run

- **Backend install:** `cd backend && py -m venv .venv && ./.venv/Scripts/pip install -r requirements.txt`
- **Backend run:** `./.venv/Scripts/uvicorn app.main:app --reload` (serves `http://localhost:8000`, health check at `/health`)
- **Backend test:** `./.venv/Scripts/pytest` (test suite added starting Phase 1)
- **Frontend install:** `cd frontend && npm install`
- **Frontend run:** `npm run dev` (serves `http://localhost:5173`)
- **Frontend build:** `npm run build` (runs `tsc -b` then `vite build`)
- **Frontend test:** `npm test` (`vitest run`)
- **Frontend lint:** `npm run lint` (oxlint)
