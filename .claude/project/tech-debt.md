# Technical debt register

Companion to [context.md](context.md) and the review gates in
[../rules/code-review.md](../rules/code-review.md).

This is the single place where **accepted** rule violations live. The `code-reviewer`
and `architect-reviewer` agents append here when a finding is consciously deferred
rather than fixed; reviewers consult it so known debt isn't re-reported as new.

## How to use

- A PR may **add** an entry when a Gate/standard violation is accepted for now — record
  enough that someone can fix it later without re-discovering the context.
- A PR that **touches** a file listed here should fix the entry (and remove it) or
  explain why it still stands.
- Keep entries specific: cite `file:line`, name the principle/anti-pattern, and give a
  concrete remediation.

| TD-9 | `backend/app/services/feed_service.py:88-109` (`backfill`/`_backfill_one`), `backend/app/services/tradingview_feed_service.py:87` (`_POLL_FETCH_COUNT`) and `:140-156` (`backfill`/`_backfill_one`) | Data-completeness gap, **more severe than originally recorded — corrected 2026-07-10**. Each poll cycle re-fetches only the most recent `_POLL_FETCH_COUNT` (20, TradingView) bars per symbol/timeframe rather than gap-detecting against elapsed wall-clock time, so an outage/backoff spell longer than that window loses the bars that closed during the excess. Worse: `_backfill_one` in **both** pipelines only checks row *count*, not recency — `if len(existing) >= _BACKFILL_CANDLE_COUNT (100): return`, before `fetch_history`/`fetch_candles` is ever called — so it is never triggered by staleness, only by an empty/thin table. The original version of this entry claimed a full app restart's `backfill()` call self-heals the gap; verified against the actual code (2026-07-10, prompted by a user question about a multi-hour machine-off scenario) that this is false — any symbol/timeframe that's been running normally already has ≥100 stored candles (100 bars is ~1.5h on M1, far less on M5/M15/H1/H4), so `_backfill_one` short-circuits on the count check and never reaches the provider, restart or not. Net effect: an outage of any length — app off, machine asleep, network down — leaves a **permanent, silent hole** in the candle data; old candles before the gap stay, live data resumes from "now" on restart, and the missing window is never backfilled from either TradingView or Twelve Data | Originally accepted as an opt-in, off-by-default pipeline's v1 trade-off; TradingView is now the default source (`Settings.tradingview_enabled=True`), so this is default-path exposure, not opt-in. Confirmed to matter for exactly the scenario a background-service deployment invites (machine off overnight/sleep/restart for updates — see [RUNBOOK.txt](../../RUNBOOK.txt), the app now runs as an always-on Windows Service), making multi-hour gaps a realistic, recurring occurrence rather than a rare edge case — worth prioritizing over the other open items, but deliberately not fixed in the same session that discovered it (scoped as its own follow-up) | **Planned fix (not started — pick up fresh):** replace both the poll-cycle window (`_POLL_FETCH_COUNT`) and the backfill row-count gate (`_BACKFILL_CANDLE_COUNT` check in `_backfill_one`) with genuine elapsed-time gap detection in both pipelines: fetch `candle_repository.get_latest(symbol, timeframe)`, compute bars-needed as `(now - latest.close_time) / timeframe_seconds(timeframe)` (fall back to a full `_BACKFILL_CANDLE_COUNT`-sized fetch when there's no existing candle at all), then request at least that many bars, capped at a sane max (e.g. 500) to bound a single request. Apply to: `feed_service.py`'s `_backfill_one`, `tradingview_feed_service.py`'s `_backfill_one`, and `tradingview_feed_service.py`'s live poll cycle (`_poll_one`/`_POLL_FETCH_COUNT`). Needs two regression tests: (1) a stale last-candle timestamp (mock `datetime.now`) asserts the fetch count scales with the gap and the missing bars actually land in the DB; (2) a pair with a *recent* last candle still only fetches the small steady-state window — no regression on the common case | 2026-07-09, corrected 2026-07-10 |
