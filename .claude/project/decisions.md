# Decisions & learnings

Companion to [context.md](context.md) and [tech-debt.md](tech-debt.md). This is the project's
durable **memory** — the *why* behind choices and the lessons learned — kept in git so the
whole team (and Claude) can rely on it later, not rediscover it.

## What belongs here

- A non-obvious **decision** with trade-offs (an approach chosen over alternatives, a library
  selected, a pattern adopted) — and *why*.
- A **learning / gotcha** that cost time and would otherwise be hit again.
- A convention adopted mid-project that isn't yet reflected in `context.md`.
- A **rejected** approach and the reason, so it isn't re-proposed.

## What doesn't

- Routine changes — those live in git history and the changelog.
- Accepted rule violations — those go in [tech-debt.md](tech-debt.md).
- Personal or cross-project facts — those belong in your own Claude Code memory, not this
  shared, committed file.

## How to use

Append a dated entry when a durable decision or learning emerges (the `architect-reviewer`
records accepted **design** decisions here too, mirroring how reviewers append to
`tech-debt.md`). Keep entries short and link the PR/issue/files. Newest first.

### 2026-07-09 — tradingview-default-source: TradingView flipped from opt-in secondary pipeline to the default, project-wide
- **Decision / learning:** After building TradingView as an opt-in second pipeline (see [[tradingview-dual-source-pipeline]]), the user asked to make it the *default* source everywhere, including a fresh clone — not just the default toggle selection in an already-running dashboard. Changed: `Settings.tradingview_enabled` default `False → True` (`app/core/config.py`); every router's `source` query param default `DataSource.TWELVE_DATA → DataSource.TRADINGVIEW` (`candles.py`, `predictions.py` x2, `signals.py` x3, `prices.py`); the frontend's `api.ts` `DEFAULT_SOURCE` and `marketStore.ts`'s initial `activeSource`, both `'twelve_data' → 'tradingview'`; `backend/.env.example` and `README.md` updated to match. The Twelve Data pipeline (or `mock`, per `Settings.feed_provider`) is unaffected and keeps running exactly as before — nothing about *how* the two pipelines operate changed, only which one every default now points at.
- **Why:** TradingView's unofficial protocol needs no API key (unlike Twelve Data, which needs `TWELVE_DATA_API_KEY`), so defaulting to it is what actually works out of the box on a fresh clone with zero configuration — a meaningful, deliberate reversal of the original "off by default, R&D-grade, don't silently depend on this" framing from when the pipeline was first built as purely opt-in.
- **Implications:** A fresh clone with no `.env` overrides now attempts a real network connection to TradingView's (undocumented, unofficial) endpoint immediately at startup — this is an intentional, confirmed trade-off, not an oversight; set `TRADINGVIEW_ENABLED=false` to opt back out to `FEED_PROVIDER`-only. [TD-9](tech-debt.md) (the poll window's outage-gap limitation) is now exposed on the default path rather than only an explicit opt-in, and its "why accepted" note was updated accordingly rather than escalated to blocking. A batch of existing integration tests (`test_candles_api.py`, `test_predictions_api.py`, `test_prices_api.py`, `test_signals_api.py`, `test_config_api.py`) that called endpoints without an explicit `?source=` — implicitly relying on the old default — were updated to pass `source=twelve_data` explicitly wherever they were testing Twelve-Data-specific behavior, and a few gained an explicit "no `?source=` at all resolves to tradingview" assertion, so the default itself is directly tested rather than only being implied by omission.

### 2026-07-09 — live-forming-candle-chart-overlay: Symbol Detail chart tracks the in-progress candle client-side
- **Decision / learning:** The user noticed the Symbol Detail chart always looked "one candle behind" TradingView's own live chart — because neither pipeline (Twelve Data's `CandleAggregator`, TradingView's `TradingViewFeedService._split_forming`) ever persists the currently-forming candle, only fully closed bars, so `GET /candles/...` (and therefore the chart) never had one to show. Fixed entirely client-side rather than adding a backend "current candle" endpoint: `utils/formingCandle.ts`'s `bucketStart`/`updateFormingCandle` fold each live price tick (already flowing into the store via `useMarketSocket`) into a running OHLC state for the *current* bucket, mirroring what the backend's own aggregator does but in the browser; `hooks/useFormingCandle.ts` wires this to `useActivePrices()[symbol]` and resets on a `symbol`/`timeframe` switch. `PriceChart.tsx` renders it via a **second, separate** `useEffect` calling `series.update()` (not the existing `setData()` effect) specifically so a live tick updates just the rightmost bar without resetting the chart's zoom/pan the way `setData()` + `fitContent()` would on every single tick.
- **A real staleness-guard bug was found and fixed during code review, then re-examined and the fix's own justification corrected.** The initial guard compared the forming candle's `open_time` against the last *closed* candle's `open_time` as raw ISO strings (`formingOpenTime <= lastClosedOpenTime`). Code review flagged that `bucketStart()`'s `toISOString()` output always carries a `.000` millisecond suffix while the backend's wire format for a whole-second timestamp typically doesn't, and that lexicographic string comparison isn't a valid proxy for chronological comparison across differently-formatted (but equally valid) ISO 8601 renderings. On closer, empirical re-derivation (confirmed via `CandleOut.model_dump_json()`, which emits `...T10:15:00Z`, never `.000` for whole seconds): given this repo's *actual* confirmed formats on both sides, the string comparison happened to agree with a proper epoch comparison in every real case — so this was not an actively-manifesting bug in this codebase specifically, just a fragile approach relying on an unstated, coincidental ASCII-ordering property of the two formats' specific difference (a `+00:00` offset instead of `Z` on either side would have broken it). Fixed by extracting `formingCandleIsStale(formingOpenTime, lastClosedOpenTime)` comparing `new Date(...).getTime()` epoch values, with tests covering both the confirmed-format case and the `+00:00` case where string comparison would have actually diverged.
- **Why:** A trader watching the chart expects to see the market moving in real time, the same way any live charting tool does — showing only historical closed bars while the price ticker itself updates live reads as broken/laggy, even though the underlying prediction/signal logic correctly only ever reacts to genuine candle closes (a separate, intentional design, not a bug — see [[tradingview-dual-source-pipeline]] for why polling-based sources especially never persist the forming bar).
- **Implications:** This is a **display-only** overlay — the forming candle is never persisted, never fed into `PredictionService`/`SignalTracker`/`SignalService`, and disappears/gets replaced the instant the backend confirms the real close via the existing `prediction`-message-triggered React Query cache invalidation. The frontend/backend timeframe-seconds duplication this introduces (`formingCandle.ts` vs. `app/utils/time.py`) is recorded as [TD-10](tech-debt.md), consistent with this monorepo's existing no-shared-schema convention. Any future code comparing timestamps that may have crossed the frontend/backend boundary should compare parsed epoch values, not raw ISO strings, even when today's formats happen to make a string comparison agree — the lesson isn't "there was a bug," it's "don't rely on an unstated formatting coincidence holding forever."
- **A second, real bug surfaced only after live usage against the actual TradingView pipeline** (neither the original implementation nor its code review caught it, since neither exercised `TradingViewFeedService` end-to-end against a live frontend): the chart still looked one candle behind even with the overlay in place. Root cause: `TradingViewFeedService._poll_one` (`app/services/tradingview_feed_service.py`) stamped the live price tick's `timestamp` with `forming.close_time` — for a still-forming bar, that's `open_time + timeframe duration`, i.e. the bucket's **future**, not-yet-real end boundary (computed in `tradingview_client.py`'s `_extract_candles`), not "now." Since that value sits exactly on the next bucket's start, `useFormingCandle`'s `bucketStart()` floored it straight into the *next* period, so the live bar was always being drawn one bucket ahead of the real currently-forming candle — which, combined with `formingCandleIsStale`'s guard, meant the actual current bucket's position on the chart never got a live update at all. Fixed by stamping the tick with `datetime.now(UTC)` instead — genuinely accurate for "when was this price observed" (also used for the price ticker's own freshness) and guaranteed to still fall inside the real current bucket, since polling happens far more often than any configured timeframe's duration. Regression test (`test_poll_one_stamps_the_live_tick_with_now_not_the_forming_bars_future_close_time`) verified against the pre-fix code via the established copy-aside/`git show`/restore technique before landing. The Twelve Data pipeline was never affected — its ticks carry real exchange-observed timestamps from `TwelveDataProvider`'s WebSocket, not a value derived from any candle boundary.
- **A third issue, also only visible from live usage: the live bar still felt stale/laggy even after the timestamp fix, confirmed by the user as "same candle count, price just lagging" (not a positional bug).** Root cause: `TradingViewFeedService._run` polled every configured `(symbol, timeframe)` pair fully **sequentially** — 3 symbols × 5 timeframes = 15 individual TradingView connect/handshake/receive/disconnect round trips per cycle, each with real network latency — so any *one* pair's live price only actually refreshed once every full rotation (tens of seconds), not every `poll_interval_seconds` (15s) as the config name implies. Fixed by polling symbols **concurrently** (`asyncio.gather` over a new `_poll_symbol(symbol)` method) while keeping timeframes **sequential within each symbol** — the coarsest-to-finest ordering (gotcha #2, see above in this same pipeline's other entry) only matters *within* one symbol, so this is safe: a 4H close on XAUUSD has no bearing on what `SignalService` reads for EURUSD. `gather(..., return_exceptions=True)` + a manual re-raise of the first collected exception, rather than letting `gather` propagate directly, so a failing symbol's coroutine can't leave the *other* symbols' work orphaned as background tasks racing the next retry cycle. Verified the speedup is real, not just plausible-sounding, via a timing-based regression test (`test_symbols_are_polled_concurrently_not_sequentially`, using an injectable per-call delay) confirmed to fail against the prior sequential code before landing.
- **Concurrency introduced a new, real (if lower-probability) failure mode that didn't exist when everything ran strictly sequentially: multiple symbols now open separate SQLite sessions at the same time, so a transient write-lock contention between them is possible.** Rather than let that escalate into `_run`'s existing "any failure backs off the whole pipeline" handling (appropriate for a genuine TradingView connectivity problem, too aggressive for a normal, self-healing SQLite hiccup), `_poll_one`'s persistence section now catches `SQLAlchemyError` specifically, logs, and returns — skipping just that one symbol/timeframe pair for this cycle; the next poll re-diffs from scratch and picks it back up. Covered by `test_a_db_error_for_one_symbol_does_not_block_or_fail_the_others`.

### 2026-07-09 — tradingview-dual-source-pipeline: TradingView added as a second, fully independent market-data source
- **Decision / learning:** Added TradingView's unofficial WebSocket protocol (no official public API for chart candles exists) as a second market-data pipeline running *simultaneously* alongside the existing Twelve Data pipeline, per an explicit user requirement that the two never share storage — directly motivated by [[remove-mock-auto-fallback]]'s incident, where a shared table with no source discriminator let mock data silently contaminate real history for ~3.5 hours. Key structural choices, each reused an existing project convention rather than inventing a new one:
  - **Not a `MarketDataProvider`.** TradingView's protocol is poll-based (connect → handshake → receive-until-`series_completed` → disconnect per fetch) and returns pre-aggregated OHLC bars (the last always still-forming), a fundamentally different shape from `stream_ticks() -> AsyncIterator[Tick]`'s continuous push of individual ticks that `CandleAggregator` buckets itself. Forcing it into the existing abstraction would either lose OHLC fidelity or fake a tick stream out of bars already aggregated — a leaky abstraction worse than two honest classes. Instead: `app/feeds/tradingview_client.py` (`TradingViewClient`, hand-rolls the `~m~<len>~m~<json>` framing over the existing `websockets` dependency — no new third-party dependency) + `app/services/tradingview_feed_service.py` (`TradingViewFeedService`, a poll-loop orchestrator mirroring `FeedService`'s backoff/reconnect philosophy but adapted to "poll cycle failed, back off" instead of "stream ended, reconnect"; does **not** use `CandleAggregator`, since TradingView already hands back pre-aggregated bars). Architect-review-confirmed: the real shared abstraction both feeds converge on is `CandleCloseHandler` ("a candle closed, run handlers") — no new `Feed` super-interface was added one layer up, since there's no third caller and no further behavior genuinely shared (would produce a fat interface).
  - **Separate ORM tables, not a `source` column.** `TradingViewCandleORM`/`TradingViewPredictionORM`/`TradingViewSignalORM` (new tables `tradingview_candles`/`tradingview_predictions`/`tradingview_signals`) mirror `CandleORM`/`PredictionORM`/`SignalORM` schema-for-schema. `Base.metadata.create_all` (already run by `init_models()`) creates them automatically on next startup — no migration step needed.
  - **Repositories/handler services parameterized by ORM model, not duplicated.** `CandleRepository`/`PredictionRepository`/`SignalRepository` each gained an optional `model` constructor param defaulting to the Twelve Data model, so `CandleRepository(session, model=TradingViewCandleORM)` reuses 100% of the tested repository logic. `PredictionService`/`SignalTracker`/`SignalService` gained the equivalent `*_model` params, so `main.py` constructs a second, fully parallel handler triad against the TradingView tables with zero duplicated handler logic.
  - **Type-safety correction (found in architect review, fixed same session):** the first pass typed these params as e.g. `type[CandleORM]`, but `TradingViewCandleORM` is a *sibling* of `CandleORM` (both extend `Base` directly), not a subtype — a real lie in the type system that only worked via runtime duck-typing on identical column names. Fixed by giving each ORM pair a shared plain (unmapped) mixin — `CandleColumns`/`PredictionColumns`/`SignalColumns` in `storage/models.py`, declaring the common `Mapped[...]` columns — so both concrete classes (`CandleORM(CandleColumns, Base)`, `TradingViewCandleORM(CandleColumns, Base)`) are genuinely `type[CandleColumns]`. This is the standard SQLAlchemy 2.0 declarative-mixin pattern; verified it maps correctly by inspecting `Base.metadata.tables` directly (all 7 tables got the right columns).
  - **`BroadcastService` gets a fixed `source` per instance** (`main.py` constructs two, one per pipeline) rather than threading a `source` parameter through every call site across `FeedService`/`TradingViewFeedService`/the three handlers. All 4 WS message schemas gained a *required* (no default) `source: DataSource` field — forces every message through the broadcaster, so one can't be constructed and silently mislabeled. Still one shared `/ws` endpoint and `ConnectionManager` — both sources' messages flow over the same connection, tagged by `source`, so the frontend toggle switches instantly with no reconnect.
  - **API routers gained a `source` query param** (originally default `twelve_data`, later changed to default `tradingview` — see [[tradingview-default-source]] in decisions.md), not a path segment — `source` is a view/filter modifier on an already-fully-identified resource (symbol+timeframe already determine "which candles"), matching the existing `limit: Query(...)` convention rather than the required-path-enum treatment `Symbol`/`Timeframe` get. Centralized in a new `app/api/source_models.py` (`candle_model_for`/`prediction_model_for`/`signal_model_for`) so routers and `main.py` share one `DataSource -> ORM model` mapping.
  - **`main.py` duplication, caught in code review:** the two ~25-line pipeline-construction blocks (Twelve Data vs. TradingView) crossed this project's own "second real caller" extraction threshold (same reasoning as TD-8). Extracted `_build_candle_close_handlers(broadcaster, session_factory, *, candle_model=..., prediction_model=..., signal_model=...)`, called twice with different keyword overrides; the two `FeedService`/`TradingViewFeedService` constructions were deliberately left separate since they genuinely differ (stream vs. poll).
  - **Two poll-specific correctness gotchas, absent from the tick-driven path, both fixed:** (1) `save_many_if_missing` doesn't report which rows were newly inserted, but the poll loop needs exactly that to know which bars are genuine "candle closed" events — fixed by diffing the fetched batch against `get_recent`'s known `open_time`s *before* persisting, in the new service, not by changing the repository's contract. (2) A single poll cycle can discover newly-closed 4H, 1H, and 15m bars simultaneously (e.g. after downtime, or at a genuine 4H boundary) — `SignalService` reads the 4H/1H windows the instant a 15m candle closes, so the coarser candles must already be persisted first or it builds against stale data. Fixed by always polling timeframes coarsest-to-finest per symbol (`_ordered_timeframes`).
  - **Frontend store reshaped to `Record<DataSource, X>` per slice** (`prices`/`predictions`/`signals`/`feedStatus`) plus one UI-only `activeSource` field, with derived `useActiveX()` selector hooks so most components changed one import line instead of threading a `source` prop themselves. React Query's cache keys (`candlesKey`/`signalHistoryKey`) now include `source` too — flagged in architect review as a second place cross-source leakage could occur even after the DB-level fix, since a TradingView candle-close invalidating the Twelve Data query cache entry for the same pair would be exactly the kind of bleed this whole feature exists to prevent.
- **Why:** The user's explicit ask was two sources running simultaneously with data kept structurally separate (not app-logic-guarded), driven by a real prior incident in this exact codebase. Every structural choice above either reused an existing project convention (parameterize-don't-duplicate, one-branch-point factories, `CandleCloseHandler`) or was validated by an `architect-reviewer`/`code-reviewer` pass before being accepted, rather than introducing new abstractions speculatively.
- **Implications:** A third data source would follow the same recipe: a new client/orchestrator pair (only if its protocol genuinely differs in shape from `MarketDataProvider`; otherwise just implement `MarketDataProvider` directly), three new schema-identical ORM tables sharing the existing `CandleColumns`/`PredictionColumns`/`SignalColumns` mixins, a new `DataSource` enum member wired into `source_models.py`, and a `_build_candle_close_handlers(...)` call in `main.py`. Known accepted limitation: `TradingViewFeedService`'s poll window (`_POLL_FETCH_COUNT`) is fixed rather than gap-detecting against elapsed wall-clock time, so an outage longer than that window silently loses those candles until the next restart's `backfill()` — see [TD-9](tech-debt.md). TD-8 (duplicated signal-build orchestration between `signals.py` and `signal_service.py`) was touched again by this feature (both gained `source`/`*_model` params) and consciously deferred a second time rather than compounding two changes in one commit.

### 2026-07-09 — rule-based-confidence-calibration: confidence scales against total possible weight, not weight present
- **Decision / learning:** Closed TD-2 — `RuleBasedStrategy._combine` previously computed `confidence = |score| / total_weight_of_votes_present * 100`, which measures *agreement* among whatever indicators happen to be available, not the *volume* of evidence behind that agreement. A single available indicator (e.g. only `structure` computed on a brand-new symbol, before enough history exists for SMA/RSI/momentum) that votes unanimously always read as exactly 100% (or 0%) confidence, identical to four indicators unanimously agreeing — no way to tell "one strong signal" from "overwhelming consensus" apart. Fixed by scaling against a new constant, `_TOTAL_POSSIBLE_WEIGHT` (sum of all 4 indicator weights = 5.0): `confidence = min(100.0, abs(score) / _TOTAL_POSSIBLE_WEIGHT * 100.0)`. An earlier draft computed this as two separate multiplied factors (`agreement = |score|/total_weight_present`, `evidence = total_weight_present/_TOTAL_POSSIBLE_WEIGHT`) to make the two calibration axes explicit — code review correctly pointed out `total_weight_present` cancels out of that product algebraically, so the two-variable form was simplified to the one-line equivalent per KISS, with `test_excluding_missing_indicators_gives_the_same_confidence_as_counting_them_neutral` kept as a regression proof of that equivalence (excluding a missing indicator vs. counting it as a neutral/zero vote now provably yields identical confidence and direction either way).
- **Why:** Confidence numbers are surfaced directly to a trader deciding whether to act on a prediction; reading "100% confidence" from a single available indicator on a symbol the system barely knows anything about yet is actively misleading, not just imprecise.
- **Implications:** Any future indicator added to `RuleBasedStrategy` must be added to `_TOTAL_POSSIBLE_WEIGHT`'s sum too, or confidence will silently under-scale (reading lower than it should once that indicator is normally available). `MLStrategy`'s own confidence (probability-derived, unaffected by this formula) is untouched. TD-2 removed from tech-debt.md.

### 2026-07-09 — websocket-driven-query-invalidation: prediction/signal messages, not price ticks, trigger candle/history refetch
- **Decision / learning:** Closed TD-4 — `useCandles`/`useSignalHistory` fetched once on mount with nothing tying them to the live WebSocket, so a page opened before the first candle closed could sit stale until manual reload. Fixed in `useMarketSocket.ts`: on a `prediction` message, `queryClient.invalidateQueries({ queryKey: candlesKey(symbol, timeframe) })`; on a `signal` message, the equivalent for `signalHistoryKey(symbol)`. `prediction` (not `price`) was chosen as the candle-staleness trigger because `PredictionService` reacts to *every* candle close for *every* symbol/timeframe — it's a reliable proxy for "this pair's candle list just changed," whereas `price` fires on every tick (far too often to invalidate on without hammering the backend). Code review flagged that inlining the query-key literals in `useMarketSocket` risked silently drifting from the real keys in `useCandles.ts`/`useSignalHistory.ts` with no test able to catch it — the exact "parallel implementation divergence" class of bug this project has already hit twice (see [[backtest-rapid-reopen-fix]], [[stale-entry-tap-and-duplicate-signal]]). Fixed by exporting `candlesKey`/`signalHistoryKey` builder functions from the two hook files themselves and importing them into `useMarketSocket`, so there's exactly one place each key shape is defined.
- **Why:** A shared key-builder function makes divergence a compile-time impossibility rather than something a test has to keep re-verifying — cheaper and stronger than either a hand-written test asserting the literal match or trusting reviewers to notice a future edit to one side.
- **Implications:** Any new React Query hook whose cache another part of the app needs to invalidate should export its `queryKey` shape as a named function the same way, rather than inlining the array literal at each call site. TD-4 removed from tech-debt.md.

### 2026-07-09 — chart-accessibility-aria-label: role="img" + computed aria-label over a visually-hidden sibling
- **Decision / learning:** Closed TD-3 — `PriceChart.tsx`'s container was a bare `<div ref={containerRef} className="w-full" />` that lightweight-charts draws a canvas into, with zero accessible content for screen readers. Fixed by adding `role="img"` and a computed `aria-label` (via a new pure function, `describeChart(symbol, timeframe, candles)` in `frontend/src/utils/describeChart.ts`) summarizing the chart's current state, e.g. "Candlestick chart for XAUUSD 15m, 200 candles, current price 4071.83". `PriceChart` gained a new required `timeframe` prop (previously only used internally by its caller `SymbolDetail.tsx`, now threaded through) so the label can name the timeframe. `role="img"` + `aria-label` was chosen over a visually-hidden sibling element with `aria-describedby`, since the canvas *is* the entire graphic with no separate interactive content needing a supplementary description — the simpler pattern is also the more correct one here. Code review caught that the new file's `FOUR_DECIMAL_SYMBOLS` set was a second, drifting copy of the one already in `PriceChart.tsx` (a real DRY violation, not incidental similarity, since both must agree on which symbols quote to 4 decimals) — hoisted both to a shared `frontend/src/utils/priceFormat.ts` exporting `pricePrecision(symbol)`, used by both the chart's actual `priceFormat` option and the aria-label text.
- **Why:** WCAG AA requires a text alternative for non-text content; a canvas chart with no `alt`/`aria-label` is invisible to assistive technology despite being the primary way this dashboard communicates price action.
- **Implications:** Any symbol added with a different natural decimal precision (e.g. a JPY pair conventionally quoted to 2-3 decimals, or crypto needing more) should extend `pricePrecision` in `priceFormat.ts`, not add a third parallel set somewhere else. TD-3 removed from tech-debt.md.

### 2026-07-09 — backfill-exception-narrowing: _backfill_one now only swallows the external failure surface it was meant to isolate
- **Decision / learning:** Closed TD-6 — `FeedService._backfill_one` caught bare `except Exception`, which correctly isolated one symbol/timeframe's backfill failure from the rest (rate limits, transient network errors, unsupported pairs) but also silently absorbed genuine coding bugs (e.g. an `AttributeError` from a real defect) as an unremarkable per-pair startup log line. Narrowed to a new module constant, `_EXPECTED_BACKFILL_ERRORS = (httpx.HTTPError, RuntimeError, KeyError, ValueError, SQLAlchemyError)` — each member justified inline (network/HTTP failure, `TwelveDataProvider`'s own API-error signal, unmapped symbol/timeframe or malformed response row, transient SQLite lock from concurrent live-feed access). Added `test_backfill_propagates_an_unexpected_error_instead_of_swallowing_it`, using `AttributeError` as a stand-in for a coding bug and asserting via `pytest.raises` that it now propagates instead of being logged-and-continued — proving the *fix's* actual point (loud failure for the unexpected case), not just re-testing the already-covered expected-failure paths.
- **Why:** A catch-all around a best-effort operation is the right shape for *known* failure modes, but silently absorbing *unknown* ones (real bugs) turns every future coding mistake in this path into a quiet log line nobody will notice until backfill mysteriously stops working for one pair.
- **Implications:** If a new expected external-failure type is discovered in real usage (e.g. a new exception `httpx` or `TwelveDataProvider` can raise that isn't yet covered), add it to `_EXPECTED_BACKFILL_ERRORS` with the same inline justification convention — don't widen back to bare `Exception`. TD-6 removed from tech-debt.md.

### 2026-07-09 — test-env-isolation: FastAPI dependency_overrides over relying on absent env vars
- **Decision / learning:** `tests/integration/test_config_api.py` asserted `body["feed_provider"] == "mock"` but failed on this machine because the real `get_settings()` dependency read the developer's actual `.env` (`FEED_PROVIDER=twelve_data`) — the same root-cause pattern already fixed once this session in `test_feed_provider_factory.py` via `Settings(_env_file=None)`. Fixed here with FastAPI's own override mechanism instead: `app.dependency_overrides[get_settings] = lambda: Settings(_env_file=None)`, applied to the test's locally-built `FastAPI()` app before the request is made.
- **Why:** `dependency_overrides` is the idiomatic FastAPI way to replace a route's dependency in a test, and reads more clearly at the call site than relying on a constructor kwarg alone to explain *why* isolation is needed.
- **Implications:** Any future router-level integration test that depends on `get_settings` (or another cached/env-derived dependency) should isolate the same way — override the dependency on the test's own `FastAPI()` instance — rather than relying on the developer's shell/`.env` not setting a conflicting value.

### 2026-07-11 — backtest-rapid-reopen-fix: a used tap candle can never reopen a signal, even after it resolves
- **Decision / learning:** After shipping [[backtest-duplicate-signal-fix]] and re-running the backtest for honest numbers, the user was rightly skeptical of a drastically worse win rate (6-11%, down from an earlier ~27-28% measured with both bugs still present) and asked to double-check rather than accept it. Tracing individual signals from a real run found a second, related bug the "one open at a time" guard didn't cover: the exact same historical tap candle could reopen a brand-new signal the instant its predecessor resolved (win/loss/expired), for as long as it remained inside the rolling 15m window (`CANDLE_WINDOW_15M=20` live, or `window_15m` in a backtest) — confirmed live in the trace: the identical entry/stop/target/opened_at signal appeared 7 times in a row, each resolving as a loss after exactly one bar, before the tap candle finally aged out of the window. Fixed by adding `eligible_entry_candles(candles, after)` (`app/prediction/signal_builder.py`) — filters the 15m candidate list to strictly-after a floor timestamp — called from both `run_signal_backtest` (tracking `last_signal_opened_at` in-memory across the walk) and `SignalService.on_candle_closed` (deriving the equivalent via `SignalRepository.get_recent(symbol, limit=1)`, since a live per-request service has no in-memory history across calls). Both fixes were verified the same way as the earlier one: copy the fixed file aside, revert the real file to the last commit, confirm the new regression test fails against the pre-fix code, then restore the fix and confirm it passes.
- **Why:** The "one open at a time" guard only prevents two signals existing *simultaneously* — it says nothing about whether a *newly* opened signal is actually new information, versus a stale rediscovery of a tap that's already been fully judged once. Treating "resolved" as "free to retry" let a single bad historical tap dominate the loss count by retrying itself repeatedly, which is exactly the kind of silent inflation backtesting exists to catch — this time in the *opposite* direction (making the setup look worse than it is, not better).
- **Implications:** `eligible_entry_candles` is the one shared home for this "strictly after the last used tap" rule — both call sites import it rather than each inlining the filter, so the eligibility rule can't silently diverge between live and backtested behavior the way context.md's shared-code philosophy already requires for `resolve_signal()`. **Any previously-reported backtest numbers (including the 6-11% figures reported before this fix) should be treated as unverified too — re-run the backtest once more after this lands.**

### 2026-07-11 — backtest-duplicate-signal-fix: run_signal_backtest now tracks one open signal at a time
- **Decision / learning:** Fixed TD-8 — `run_signal_backtest` (`app/backtesting/signal_backtest.py`) previously called `build_signal()` unconditionally at every 15m step and fast-forward-resolved each result immediately using all remaining future candles in one shot (`_resolve_forward`), appending every non-None result to `signals` with no check for whether a signal from an earlier step was still open. This meant the exact same rediscovered setup (identical entry/stop/target, same `opened_at`) could be appended as multiple separate "signals," inflating `total_signals` and skewing `win_rate`/`avg_realized_rr` — the same bug already fixed for the live path (see [[stale-entry-tap-and-duplicate-signal]]), just not touched by that fix since this engine calls `build_signal()` directly rather than through `SignalService`. Restructured the walk-forward loop to track a single `open_signal: Signal | None` and, at each step, first call `resolve_signal()` against just that one new candle (mirroring `SignalTracker`'s live behavior, not `_resolve_forward`'s old fast-forward-through-everything shortcut), and only consider `build_signal()` again once no signal remains open (mirroring `SignalService`'s `get_open()` guard). A new regression test (`test_does_not_create_a_duplicate_signal_while_one_is_already_open`) reproduces the exact live mechanism — a wider-than-1 rolling `window_15m` keeps the original tap candle "in view" across a later step that neither resolves nor re-taps the zone on its own — and was confirmed to fail (2 signals) against the pre-fix code via `git stash` before being confirmed to pass (1 signal) with the fix.
- **Why:** A backtest's only purpose is producing trustworthy win-rate/R:R numbers to decide whether the live signal pipeline is worth trusting — duplicate-inflated numbers are worse than no backtest at all, since they look credible without being so. This closes the exact gap TD-8 flagged as unverified.
- **Implications:** All 6 pre-existing `test_signal_backtest.py` tests were re-verified to still pass unchanged (traced through by hand before running, then confirmed) — none of their fixtures exercised the duplicate-rediscovery scenario, so none needed updating. **Any previously-reported backtest win-rate/avg-realized-RR numbers should be re-derived by re-running the CLI now** (`python -m app.backtesting.cli`) rather than trusted from before this fix.

### 2026-07-11 — additive-schema-migration: startup ALTER TABLE for missing columns, no Alembic yet
- **Decision / learning:** `init_models()` (`app/storage/database.py`) previously only ran `Base.metadata.create_all`, which creates missing *tables* but never alters an existing table's columns — the exact gap TD-9 recorded when `Signal.created_at` needed deleting and recreating the whole dev DB. Added `app/storage/migrations.py`'s `add_missing_columns(conn, Base)`, called right after `create_all` inside the same `engine.begin()` transaction: it inspects each table already present via `sqlalchemy.inspect(...).get_columns()`, diffs against what the current ORM model declares, and runs `ALTER TABLE ... ADD COLUMN ...` for anything missing — always nullable regardless of the model's own declared nullability, since a pre-existing row genuinely has no value for a brand-new column (NULL is the honest answer for it, not a fabricated backfill). A real gotcha hit while building this: `Base.metadata` is only populated once every module defining an ORM class has actually been *imported* somewhere in the process — calling this from an isolated script/test that only imports `app.storage.database` (not `app.storage.models`) silently sees an empty `metadata.sorted_tables` and does nothing, no error. Fixed by having `init_models()` explicitly `from app.storage import models` (function-local, to avoid a circular import with `database.py`) before touching `Base.metadata`, rather than relying on some other already-imported module to have pulled it in first as a side effect.
- **Why:** The project has no Alembic (or other migration tool) and, per TD-9, "just delete the dev DB" was becoming a real recurring cost, not a one-time inconvenience — this happened twice in one day. A full migration tool is more machinery than this stage of the project needs (see the project's existing lightweight-tooling bias — hand-rolled fakes over mocking libraries, no ORM-migration framework at all until now); an additive-only, purely mechanical column-adder closes the specific gap that's actually been hit without adopting new tooling or requiring a hand-written migration script per schema change.
- **Implications:** This deliberately does **not** handle renames, type changes, constraint changes, or column/table removal — those still need a real migration tool, and attempting them through this mechanism would either silently do the wrong thing or fail outright. If the schema starts needing that kind of change regularly, that's the real signal to adopt Alembic — don't extend this function to cover it. Any future test that calls `add_missing_columns` (or otherwise touches `Base.metadata`) directly, without going through `init_models()`, must import `app.storage.models` itself first for the same reason.

### 2026-07-08 — idempotent-live-candle-save: CandleRepository.save() no longer raises on a duplicate (symbol, timeframe, open_time)
- **Decision / learning:** `CandleRepository.save()` (the live single-candle path, called from `FeedService._persist`) used to `INSERT` unconditionally and let a duplicate-key violation propagate, on the reasoning that a live duplicate should always be a real bug. Observed live, repeatedly, right after recreating the DB and restarting: the exact same `(symbol, timeframe, open_time)` was submitted for insertion multiple times in a row across consecutive 1m candles for both XAUUSD and EURUSD — not a single one-off restart-boundary overlap (which was the original, narrower hypothesis recorded and since removed from tech-debt.md), but a sustained pattern. Since `FeedService._handle_closed_candle` wraps `_persist()` **and every downstream handler** (`PredictionService`, `SignalTracker`, `SignalService`) in one try/except, each duplicate-key exception was silently skipping prediction/signal processing for that candle close entirely, every single time it happened — a real, recurring loss of processing, not just log noise. `save()` now uses the same `sqlite_insert(...).on_conflict_do_nothing(index_elements=...)` idiom `save_many_if_missing` already used for backfill, making a duplicate call a no-op instead of an exception. `FeedService`'s handler loop is unchanged — it already runs unconditionally after `_persist()` returns, so it now correctly always runs, whether this specific call persisted a new row or the row already existed.
- **Why:** Whatever the exact mechanism producing the repeated duplicate submissions (a live provider re-delivering the same tick/candle boundary around a reconnect, or `uvicorn --reload` restarting the process again while ticks for the same boundary are still in flight, or some other overlap) — treating every duplicate as a fatal error for that candle's entire downstream processing was the wrong response to what is, in practice, a routine occurrence for a live streaming feed, not evidence of a coding bug each time it fires. Prediction/signal handlers are safe to re-run against a candle whose data hasn't changed: `PredictionService` just recomputes and rebroadcasts, `SignalTracker`'s resolution check is idempotent, and `SignalService`'s duplicate-open-signal guard (see [[stale-entry-tap-and-duplicate-signal]]) already prevents an actual duplicate signal row regardless of how many times `on_candle_closed` fires for the same candle.
- **Implications:** A duplicate live candle submission is now silent (no log line at all) rather than logged-and-skipped — if this starts happening so often it's worth investigating the root cause (rather than just tolerating it), that will need a deliberate log/metric added back in, since this fix intentionally makes the common case invisible. If a *second* overlapping live process turns out to be the actual cause (e.g. two terminals each running their own `uvicorn`, or an incomplete `--reload` teardown), this fix doesn't prevent the waste of running two live feeds — it only prevents the resulting duplicate-insert from silently dropping prediction/signal processing. Worth checking for a stray second backend process if this was observed happening unusually persistently.

### 2026-07-08 — stale-entry-tap-and-duplicate-signal: entry taps must postdate the zone's own confirmation, and one open signal per symbol at a time
- **Decision / learning:** A real live XAUUSD signal was traced end-to-end against the actual stored candle data (direct read-only SQLite inspection, then re-running `_find_setup()`/`build_signal()` against reconstructed historical windows) and revealed two related defects in `app/prediction/signal_builder.py` and `app/services/signal_service.py`. (1) `_check_entry()` scanned the last 20 15m candles for *any* price-range overlap with the entry zone, with no regard for whether the zone existed yet when a given candle closed — the OTE zone depends on `leg_end` (the extreme point after the confirming structure break), which is only known once that 1H candle has actually closed. In the traced case, `_find_setup()` returned nothing at all when replayed against data truncated at 09:00/10:00/11:00/12:00 UTC, and only started producing this exact setup once the cutoff reached 13:00 UTC — yet the persisted signal's `opened_at` was 08:30 UTC, because a 15m candle from *before* the zone was computable (part of the original impulsive move, not a genuine retracement) was still sitting inside the trailing 20-candle window by the time the setup became valid. Checking the full 15m candle path confirmed price never actually returned to the zone after the leg completed — and had already reached the signal's `target` at 10:00 UTC, nearly 3 hours *before* the signal was even created. Fixed by adding `_Setup.earliest_entry_time` (`candles[leg_end_index].close_time`) and requiring `_check_entry`'s tap candle to have `close_time` strictly after it (candles are ascending, so an early `break` suffices once one candle fails the check). (2) Separately, `SignalService.on_candle_closed` had no guard against an already-open signal for the same symbol — confirmed via direct DB inspection that two persisted rows had byte-identical entry/stop/target/reason and the exact same `opened_at`, produced by two different 15m-close invocations both independently rediscovering the same still-valid setup (since `build_signal()` is a pure, stateless rescan — nothing invalidates a setup just because it was already acted on once). Fixed with a `SignalRepository.get_open(symbol)` check at the top of `on_candle_closed`, before even fetching candle windows.
- **Why:** Both bugs share a root cause — the signal pipeline treats "does this rolling window currently satisfy the rules" as the only question, with no memory of *when* a fact became true or whether it's already been acted on. That's fine for whether a setup exists in principle, but wrong for deciding whether a specific candle is a genuine reaction to it, and wrong for deciding whether to create a *new* signal when one is already tracking the same setup.
- **Implications:** `Signal` gained a `created_at: datetime` field (`field(default_factory=lambda: datetime.now(UTC))`), deliberately distinct from `opened_at` (the tap candle's close_time, a fact about market data that can legitimately sit hours before the row's actual insert time) — added specifically so this class of "when did this really happen" question is answerable directly from the DB next time, without needing to re-derive it from raw candle data. `SignalORM` gained a matching non-nullable column; **any pre-existing SQLite `market_predictor.db` needs deleting/recreating** before the app can save a new signal (`init_models()`'s `Base.metadata.create_all` doesn't add columns to existing tables — no migration tool exists yet, see [TD-9](tech-debt.md)). `_build_details` now also persists `earliest_entry_time` in the signal's `details` JSON for the same reason. The backtest engine (`app/backtesting/signal_backtest.py`) has the identical duplicate-signal exposure and was **not** fixed here — recorded as [TD-8](tech-debt.md), since fixing it needs the walk-forward loop restructured to track "open as of now" rather than fast-forward-resolving each signal fully at append time; any previously-reported backtest win-rate numbers should be treated as unverified against duplicate-inflation until that lands.

### 2026-07-08 — chart-rescale-on-symbol-switch: `series.setData()` doesn't reset the visible time window

### 2026-07-11 — ml-training-in-sample-contamination: train.py's own auto-comparison retested the model on its own training data
- **Decision / learning:** The first version of `app/ml/train.py` fit a `RandomForestClassifier`, computed a correct holdout accuracy via a clean chronological split, then — in the same run — called `run_prediction_backtest(symbol, timeframe, candles, strategy=MLStrategy(model_dir=model_dir))` over the **full fetched history** (all 5000 candles) to compare against the rule-based baseline "for a direct, same-run comparison." Running the real XAUUSD/1h training confirmed this was a real bug, not a theoretical one: the genuine holdout accuracy was 53.7%, but the "walk-forward" comparison reported 83.2% for the *same* freshly-trained model — because that walk only used `candles`, not the held-out slice, so ~80% of it was re-testing the model on rows it had just memorized during `.fit()`. Fixed by removing the auto-comparison entirely; `train.py` now only prints the clean holdout accuracy. Deliberately did **not** add a `--strategy ml` option to `app/backtesting/cli.py` as an alternative way to get this comparison — doing so correctly requires evaluating only on the model's true held-out slice, and that CLI has no way to know where a given saved model's split boundary was (it fetches its own history independently from `train.py`'s run). Building a version of that feature without solving the boundary-tracking problem would just relocate the same bug, not fix it.
- **Why:** An in-sample-contaminated number silently degrades trust in every future accuracy this project reports if it doesn't get caught early — 83.2% would have been recorded in docs as "ML beats rule-based decisively," which was never actually true. The bug was also independently a performance problem (evaluating one row at a time on a 200-tree forest across ~4000+ rows took minutes per pair, making the intended 15-pair sweep impractical), but fixing only the speed and not the leak would have kept shipping a wrong number faster.
- **Implications:** `train.py`'s printed `holdout_accuracy` is the only trustworthy number for judging a trained `MLStrategy` model — never re-derive an "accuracy" by running `run_prediction_backtest` over arbitrarily-refetched history against a model that might have trained on part of it. If a genuine walk-forward re-verification of a saved model is ever needed, the split boundary (e.g. the training run's cutoff timestamp) must be persisted alongside the model file and the backtest must be scoped to strictly-after that boundary — don't build a shortcut that skips this.

### 2026-07-11 — ml-prediction-strategy: per-(symbol,timeframe) RandomForest models behind the existing PredictionStrategy seam
- **Decision / learning:** Phase 9 Part C added `MLStrategy` (`app/prediction/ml_strategy.py`), a `RandomForestClassifier`-backed `PredictionStrategy` — one trained model per (symbol, timeframe) pair (15 total, chosen over pooling all 3 symbols into 5 timeframe-only models, trading data volume per model for instrument-specific fit), selected via `Settings.prediction_strategy` (`rule_based`/`ml`) through a new `app/prediction/factory.py` mirroring the feed-provider factory pattern. - **Implications:** Trained `.joblib` files live under `Settings.ml_model_dir` (default `data/models/`) and are gitignored — regenerable binary artifacts, not source, and re-running `train.py` overwrites them deterministically (`random_state=42`). Any future strategy that's genuinely symbol/timeframe-specific should follow the same pattern (resolve internally from the `FeatureSet` it's given) rather than trying to make `get_prediction_engine()` per-parameter — that would ripple into every caller of `PredictionEngine`.

- **Decision / learning:** Running the backtest CLI for real against the live Twelve Data account exposed the actual API key in plain text in terminal output — `httpx` logs full request URLs, including query parameters, at `INFO` level, and `TwelveDataProvider.fetch_history` was passing `apikey` as a query param (`params={"apikey": self._api_key, ...}`). ### 2026-07-10 — backtesting-engine: walk-forward replay reuses live strategy code unmodified, windowed via a two-pointer walk
- **Decision / learning:** The backtest engine (`app/backtesting/`) doesn't reimplement `build_signal()`/`RuleBasedStrategy` in any way — it calls the exact same functions the live pipeline calls, just supplying historical candle windows instead of "whatever's currently in the DB." Avoiding lookahead bias is the entire point of a backtest, so `run_signal_backtest` maintains a monotonically advancing pointer per timeframe (`_advance`) rather than re-filtering the full candle list by timestamp at every 15m step — both are correct, but the pointer approach is O(n) instead of O(n·m), which matters once a run covers 5000 candles per timeframe. `resolve_signal()` was extracted from `SignalTracker` into `app/prediction/signal_resolution.py` as a pure function specifically so backtested outcomes are graded by the identical rule live ones are, not a parallel reimplementation that could quietly drift. A dedicated regression test (`test_does_not_leak_future_1h_candles_into_an_earlier_15m_step`) proves the windowing is correct: the same price tap produces a signal once all 18 required 1H candles are visible, and produces none when only the first 10 are — confirmed via the real `build_signal()` behavior, not a mock.
- **Why:** A backtest that could see the future (even accidentally, through sloppy windowing) would produce meaningless, inflated win rates — worse than no backtest at all, since it would look trustworthy. Reusing live code instead of a parallel implementation means the backtest is honestly testing what the live system actually does, not a hopefully-equivalent stand-in. `run_signal_backtest`/`run_prediction_backtest` both accept their window sizes as overridable parameters (defaulting to the real live constants from `signal_service.py`/`engine.py`) purely so tests can exercise the walk-forward/warmup logic with small fixtures instead of needing 60+/100+/20+ real candles per test.
- **Implications:** Any future change to `build_signal()`, `resolve_signal()`, or `RuleBasedStrategy` automatically changes backtest behavior too — there is nothing else to keep in sync. The CLI (`app/backtesting/cli.py`) fetches history via a bare `TwelveDataProvider`, not through `create_provider()` — a backtest must always use real data regardless of the running app's configured `feed_provider`, and must fail loudly on a real fetch problem (bad key, rate limit), not silently substitute the mock feed's much shorter synthetic history and produce a backtest that looks valid but measured nothing real. (`create_provider()` itself no longer wraps anything in a fallback at all as of [[remove-mock-auto-fallback]] — this CLI's reasoning for going around it stands regardless.)

### 2026-07-10 — fallback-provider-chain: FeedService reads nominal_status live, not once at construction
- **Decision / learning:** Phase 9 Part B added `FallbackMarketDataProvider` (`app/feeds/fallback_provider.py`), a composite that tries a priority-ordered list of providers — `create_provider` now wraps `[TwelveDataProvider, MockMarketDataProvider]` whenever a real feed is selected, satisfying PROJECT.md's "safe fallback if live feed is unavailable" rule. It falls back to the next provider **immediately inside a single `stream_ticks()` call** the moment the current one fails (not waiting out FeedService's own reconnect backoff — the two mechanisms compose, they don't duplicate each other), and deliberately ends the stream after a bounded `fallback_max_duration_seconds` (default 300s) while parked on a fallback, purely so FeedService's existing "stream ended → reconnect → retry" handling gives the primary another chance periodically — reusing Phase 8's retry loop as the "try the primary again" driver instead of building a second, bespoke timer mechanism. This required removing the `self._nominal_status` attribute `FeedService` cached once at construction (Phase 8/9 Part A) — it now calls `self._provider.nominal_status` fresh every time it needs to broadcast recovery, since a composite provider's nominal status genuinely changes over time (LIVE while on the primary, MOCK while degraded to the fallback), unlike either single provider it wraps.
- **Why:** `FeedService`'s per-provider reconnect-with-backoff (Phase 8) already handles a *single* provider disappearing and coming back, but not a primary provider being reliably down for a while — retrying the same dead provider every 30s (the backoff cap) forever, with no fallback, means predictions/signals go stale indefinitely on a real outage. Verified live: booting with `FEED_PROVIDER=twelve_data` reports `feed_status: "live"` over `/ws` (the primary, not the mock fallback) when the primary is healthy, confirming the wrapper delegates correctly in the common case.
- **Implications:** Any future third provider just gets added to the list passed to `FallbackMarketDataProvider` in `factory.py` — no changes needed to `FeedService` or the fallback provider itself. If a provider's `nominal_status` is ever read and cached anywhere else in the codebase (there's only the one call site today), it must be re-read live, not cached, for the same reason.

### 2026-07-09 — historical-backfill: FeedService.backfill() runs before start(), not folded into it
- **Decision / learning:** `FeedService` gained a `backfill()` method (Phase 9 Part A) that fetches up to `_BACKFILL_CANDLE_COUNT=100` closed candles per configured symbol/timeframe via `provider.fetch_history()` and persists them with the new `CandleRepository.save_many_if_missing()` (idempotent — `ON CONFLICT DO NOTHING` on the existing unique index, so re-running backfill after a restart doesn't crash on overlapping rows). It's called explicitly from `main.py`'s `_lifespan` before `feed_service.start()`, not automatically inside `start()` itself. Each symbol/timeframe backfill is wrapped individually so one failure (rate limit, transient network error) logs and moves on rather than aborting the rest or blocking app startup entirely.
- **Why:** The ICT signal pipeline needs 60 closed 4H candles (10 real days), 100 1H candles (~4 days), and 20 15m candles (~5 hours) *per symbol* before `build_signal()` can produce anything (`services/signal_service.py`'s `_CANDLE_WINDOW_*` constants); the rule-based predictor wants 100 candles per timeframe too. Against a real feed running at actual market speed, that's a real multi-day blackout with zero predictions or signals on every fresh boot/redeploy — not acceptable, and the reason this was scoped as required Phase 9 work rather than a nice-to-have. Verified live end-to-end: booting with `FEED_PROVIDER=twelve_data` against a real API key produced real backfilled candles across all three symbols within ~2 minutes (rate-limited to Twelve Data's free-tier 8 req/min), and `GET /predictions/XAUUSD/1h/latest` returned a real, non-degenerate prediction immediately on that same fresh boot.
- **Implications:** Keeping `backfill()` a separate, explicit call (rather than baking it into `start()`) keeps it independently testable and keeps `start()`'s job (connect + launch the live loop) unchanged from Phase 8. A future provider only needs to implement `fetch_history()` faithfully (return `[]` if it has no historical concept, like `MockMarketDataProvider`) to get backfill for free — no changes needed to `FeedService`.

### 2026-07-09 — volume-profile-zero-volume-guard: compute_volume_profile returns None for all-zero volume input
- **Decision / learning:** `compute_volume_profile` (`app/features/volume_profile.py`) now returns `None` when `sum(volumes) <= 0`, in addition to its existing empty-input/zero-range guards. Before this, all-zero volume input still produced a `VolumeProfile` — `max(range(bin_count), key=lambda i: bin_volumes[i])` picks the *first* index on an all-zero tie, so the "POC" was always just the low edge of whatever range was profiled: a silent, systematic bias, not a graceful degradation.
- **Why:** This was purely theoretical until Phase 9 Part A's `TwelveDataProvider` — real forex/commodity data has no volume at all (see [[twelve-data-provider]]), so this bug would have started firing on every real signal the moment a live feed was wired in, silently skewing `_pick_best_zone`'s POI tiebreak in `signal_builder.py` toward the wrong side of every leg. `signal_builder.py` already handled `volume_profile is None` correctly (falls back to the first candidate zone) — it just needed `compute_volume_profile` to actually report "no usable signal" instead of a fabricated one.
- **Implications:** Any future volume-dependent feature must check for exactly this: real per-candle volume being genuinely absent (all zero) is a **different** condition from a valid-but-uninteresting volume distribution, and the two must not be conflated. If a future feed reports partial/sparse volume (some candles zero, most not), this guard would *not* catch that case — it only guards the all-zero case that OTC feeds hit universally.

### 2026-07-09 — feed-reconnect-backoff: FeedService retries a failed tick stream instead of dying silently
- **Decision / learning:** Before Phase 8, `FeedService._run` caught any exception from the provider's `stream_ticks()` and just logged "Feed loop terminated unexpectedly" — the feed died permanently until a process restart, and `self.status` never moved off its initial value (docstring literally said "status is fixed; revisit once a provider that can actually degrade/disconnect exists" — this is that revisit). `_run` now retries in a loop with capped exponential backoff (`_INITIAL_RECONNECT_DELAY_SECONDS=1.0` → `_MAX_RECONNECT_DELAY_SECONDS=30.0`, doubling via `_RECONNECT_BACKOFF_MULTIPLIER`), calling `disconnect()`/`connect()` again before each retry, and broadcasting `FeedStatus.DISCONNECTED` for the duration. A stream ending cleanly (no exception) is treated the same as a failure — the `MarketDataProvider` contract says a provider streams "until disconnected," so the generator returning on its own is still an unexpected disruption, not a graceful shutdown (`stop()` uses task cancellation instead).
- **Why:** `MockMarketDataProvider` never actually raises today, so this was invisible — but a real feed adapter (Phase 9) will drop connections, and without this the entire pipeline (candles, predictions, signals) would go silently stale after one transient network blip. `FeedStatus.DEGRADED` is deliberately left unused for now — it's reserved for a future heartbeat/stall detector (ticks arriving, but abnormally slowly), a different failure mode from the hard stream failure this handles, and building that detection now would be speculative (YAGNI) since `MockMarketDataProvider` has no notion of "stalled but technically connected."
- **Implications:** A real feed adapter can rely on this retry loop rather than implementing its own — it only needs to raise (or let its generator end) on failure and support being `connect()`-ed again after `disconnect()`. If/when a heartbeat-based stall detector is built, it's a second, independent mechanism (likely a watchdog timer alongside the tick loop) that should set `FeedStatus.DEGRADED`, not be folded into this exception-driven path.

- **Decision / learning:** Phase 8 added `add_security_headers` (`app/core/security_headers.py`), a `@app.middleware("http")` function setting `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Strict-Transport-Security` on every HTTP response. ### 2026-07-07 — Zustand selector gotcha: derived arrays/objects need useShallow
- **Decision / learning:** `SignalFeed.tsx` crashed the dashboard (blank page, `"The result of getSnapshot should be cached to avoid an infinite loop"`) using `useMarketStore(selectOpenSignals)` where `selectOpenSignals` does `Object.values(state.signals).filter(...).sort(...)` — a new array every call. Zustand v5's `useSyncExternalStore`-based subscription sees a "changed" snapshot on every render (new array reference) and loops. Fixed by wrapping the selector: `useMarketStore(useShallow(selectOpenSignals))` from `zustand/react/shallow`, which compares the array's *elements* instead of its reference.
- **Why:** This only bites *derived* selectors (filter/map/sort producing a new container). Selectors that just read a stored slice directly (`state.feedStatus`, `state.prices[symbol]`) are fine as-is, since Zustand's `set` only replaces that reference when the slice actually changes.
- **Implications:** Any new Zustand selector in `marketStore.ts` that filters/maps/sorts/derives a new array or object must be wrapped in `useShallow` at every call site (not just once) — the store can't enforce this for you. Plain slice reads don't need it.

### 2026-07-07 — react-query for REST bootstrap, zustand for WebSocket-pushed state
- **Decision / learning:** The frontend uses two different state tools for two different data shapes: `@tanstack/react-query` for one-shot REST fetches that seed initial state (`useSymbols`, `useOpenSignalsBootstrap`), and `zustand` (`store/marketStore.ts`) for everything the WebSocket pushes live (prices, predictions, signal open/resolve events).

But WebSocket-pushed updates aren't "server state" in that pull/cache sense; they're push events the UI must apply as they arrive, which is exactly what a lightweight global store is for. Bootstrapping open signals via react-query and then having `useMarketSocket` update the same `zustand` slots (keyed by signal `id`) keeps both tools doing the job they're actually good at, rather than forcing one to do both.
- **Implications:** New REST-fetched data that doesn't change live → add a react-query hook. New WebSocket message types → add a store slice + dispatch case in `useMarketSocket.ts`, not a react-query hook.

### 2026-07-07 — SignalORM's in-place mutation is bounded to outcome fields only
- **Decision / learning:** `SignalORM` is the one table in this schema mutated after insert (`SignalRepository.update_outcome` overwrites `status`/`closed_at`/`realized_rr`) — every other table (`CandleORM`, `PredictionORM`) is append-only. This was reviewed and accepted: the plan fields set at OPEN (`entry`/`stop`/`target`/`reason`/`details`) are never touched by `update_outcome`, only the outcome fields transition, so "what did we predict and why" is never lost — only "did it resolve" changes in place.

### 2026-07-07 — UTCDateTime column type: SQLite silently drops tzinfo on read-back
- **Decision / learning:** `SignalRepository` tests (`test_update_outcome_resolves_a_signal_to_win`, `test_get_recent_returns_ascending_order_by_opened_at`) failed comparing a round-tripped datetime against a constructed `tzinfo=UTC` one — SQLite's stdlib driver stores `DateTime(timezone=True)` values as naive strings and returns naive `datetime` objects, silently dropping tzinfo. This was a **pre-existing** bug affecting `CandleORM.open_time`/`close_time` and `PredictionORM.timestamp` too — it just hadn't surfaced because no earlier test compared a round-tripped datetime object directly against a tz-aware one (JSON-serialized timestamps and `.close`/`.price` field comparisons masked it). Fixed at the root with a `UTCDateTime` `TypeDecorator` (`backend/app/storage/types.py`) that rejects naive input on write and reattaches `tzinfo=UTC` on read; all `DateTime(timezone=True)` columns across `CandleORM`, `PredictionORM`, and `SignalORM` now use it.
- **Why:** The Signal outcome-tracker (next task) needs `datetime.now(UTC) - signal.opened_at` to compute expiry — a naive/aware mismatch there raises `TypeError` immediately, not just a wrong-but-silent value, so this had to be fixed before that work rather than deferred.
- **Implications:** Any new datetime column must use `UTCDateTime` from `app.storage.types`, never `DateTime(timezone=True)` directly. All datetimes in this codebase are UTC by convention (`datetime.now(UTC)`) — `UTCDateTime` enforces that at the write boundary rather than silently accepting naive datetimes that would corrupt comparisons later.

### 2026-07-06 — event-driven-prediction-scheduling: candle close drives prediction runs, not a polling scheduler
- **Decision / learning:** Phase 4 wires `FeedService` to call `PredictionService.on_candle_closed()` every time `CandleAggregator` closes a candle, rather than adding an APScheduler-style polling loop (PROJECT.md's stack list mentions APScheduler as an option, but doesn't require it).
- **Why:** A fresh prediction is only meaningful once a new candle has actually closed — polling on a fixed interval would either recompute against unchanged data (wasted work, and duplicate near-identical log rows) or need its own logic to detect "has a new candle closed since I last ran," which the tick stream already tells us for free. The tick stream is the natural schedule.
- **Implications:** There's still no throttling on the REST `GET /predictions/{symbol}/{timeframe}/latest` endpoint from Phase 3 — it computes+logs on every call regardless of candle state, so calling it repeatedly still produces duplicate log rows (a pre-existing, documented v1 behavior, now joined by the automatic candle-close predictions). If a real polling scheduler is ever needed (e.g. a future feed that doesn't emit a clean tick stream), add it as a new `services/` module behind the same `PredictionService.on_candle_closed`-style entry point — don't duplicate the prediction-triggering logic inside `FeedService`.

### 2026-07-06 — async-sqlalchemy-decision: SQLAlchemy async engine + aiosqlite over sync SQLAlchemy
- **Decision / learning:** The Phase 1 storage layer (`backend/app/storage/database.py`) uses SQLAlchemy's async engine with the `aiosqlite` driver (`sqlite+aiosqlite:///...`), not the default synchronous SQLite driver.
- **Why:** The candle-ingestion loop (`FeedService._run`) is an `async for` over the tick stream; a sync DB call there would block the event loop on every candle close. Matches the "async I/O throughout, no sync-over-async" convention already set in Phase 0.
- **Implications:** Any future repository/table must go through the async engine (`get_engine()`/`get_session_factory()` in `storage/database.py`, both lazily constructed and `lru_cache`d — never build the engine at import time, or tests lose the ability to override `get_session()` per-request). `DATABASE_URL` must always carry the `+aiosqlite` (or future Postgres equivalent's async driver) suffix. If SQLite is later swapped for Postgres, use `asyncpg`, not `psycopg2`.
